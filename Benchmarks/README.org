#+TITLE: LeanPoo benchmarks

These programs measure C4 traversal, declaration construction, dispatch,
layout lookup, revision, memoization, and mutable composition. Run a named
~just benchmark-*~ recipe; these measurements are separate from the project
test gate. They do not establish a general performance guarantee.

~just benchmark-strict-definition~ compares ordered replacement construction
with duplicate-checked construction on distinct keys at three scales.

~just benchmark-schema-merge~ compares repeated pairwise merging with the
shared-index pass over disjoint families. It checks node counts and inherited
declaration checksums before reporting timings.

Usage scenarios live in [[file:../Examples/README.org][Examples]], and assertions live in
[[file:../Tests/README.org][Tests]].

~just benchmark-check-startup~ compares repeated Lake launches with batched
cached builds and an already configured Lean environment. It alternates A/B
order over three repetitions, requires identical Lean check transcripts, and
reports CPU and wall time separately. ~CheckStartup.py --output receipt.json~
saves samples and exact Lean-source hashes. These are warm pipeline startup
measurements, not C4 algorithm throughput or a whole-suite speedup claim.

See [[file:../docs/check-performance.org][check pipeline performance]] for the measured boundary and full gate policy.


~python3 Benchmarks/EulerMaintenanceStudy.py --output /tmp/euler-maintenance.json~
is an optional source/maintenance study, not a runtime benchmark. It requires
and only reads the pinned clean ~.data/NavierStokesAndEuler~ reference. It counts
common explicit arguments and marked code sections in the kernel-checked
~Tests/FunctionalMaintenance.lean~ comparison, including checklist/application
code and shared library costs. It runs no upstream builds. See the
[[file:../docs/use-cases/euler-maintenance-checklist.org][benefit checklist]] and tracked receipt for scope and unknown adapter costs.


The study's v2 receipt also includes marked positional/named access definitions
from ~Tests/FunctionalAccess.lean~, additional shared Access/proof-adapter code,
and the source declaration/context-slot/adapter-arity inventory. The original
v1 receipt remains a historical preparation-only baseline. Full implicit
instance/context/adapter elaboration and global source savings remain unknown.

~python3 Benchmarks/EulerChangeSurfaceStudy.py --output /tmp/euler-change-surface.json~
reads only Git-tracked Lean files at the pinned clean Euler reference. The
[[file:receipts/euler-change-surface-2026-10-04.json][receipt]] records a content manifest, physical line/file counts, lexical mentions
of the four earlier theorem entry points outside their defining file, and
hashes of the local projection contract and test. It does not resolve Lean
references or measure affected consumers, source savings, or runtime. It is
optional reference research and is not a CI dependency. The [[file:../docs/use-cases/euler-maintenance-checklist.org][evaluation protocol]]
now prioritizes real change fanout and complete migration costs.
