#+TITLE: POOF, Gerbil-POO, and C4-Mixins: source map

| Repository | Source | Role |
|------------+--------+------|
| [[https://github.com/metareflection/poof][POOF]] | ~poof-code-only.rkt~ | Functional account and executable Racket examples |
| [[https://github.com/tao3k/gerbil-poo][Gerbil-POO]] | ~proto.ss~, ~object.ss~, ~mop.ss~, ~type.ss~ | Prototype, object, and expression layers |
| [[https://github.com/fare/c4-mixins][C4-Mixins]] | ~include/c4/linearize.hpp~ | C++20 C4 linearizer |

* What the sources establish

1. *Start with prototype composition and instantiation.* POOF's
   ~poof-code-only.rkt~ defines ~fix~ and ~mix~, then demonstrates slot
   constructors that can use ~self~, an inherited value, or both. Gerbil-POO's
   ~proto.ss~ gives the corresponding small ~instantiate-proto~,
   ~compose-proto~, and ~instantiate-protos~ layer. This is the smallest
   semantic core for the later Lean object layer.
2. *Keep a prototype distinct from its computed instance.* Gerbil-POO's
   ~doc/poo.md~ explains the distinction, while ~object.ss~ stores direct
   slots, supers, computed slot functions, a precedence list, and a cached
   instance. A Lean model should say which of these are mathematical values
   and which are implementation caches before adopting the Gerbil structure.
3. *Treat multiple inheritance as a separate layer.* The POOF Racket example
   contains ~c3-compute-precedence-list~, not C4. Gerbil-POO
   ~object.ss~ calls Gerbil runtime ~c4-linearize~, checks cycles, and uses the
   resulting order to assemble inherited slot functions. POOF is useful for
   the prototype model, but cannot by itself serve as a C4 oracle.
4. *Add types and generic dispatch after the object core.* Gerbil-POO's
   ~mop.ss~ defines generic functions that dispatch through prototype slots
   and runtime type descriptors; ~type.ss~ then builds tuples, lists, unions,
   records, and other descriptors. These are useful reference designs, but
   should not be presumed part of the minimal POO model.
5. *Use the actual C++ source for C4.* POOF's ~cpp/README.md~ points to
   ~fare/c4-mixins~; it does not contain the implementation. C4-Mixins has a
   generic linearizer in ~include/c4/linearize.hpp~, a mixin adapter in
   ~include/c4/mixins.hpp~. Its API supports multiple local parent orders and
   suffix classes; Gerbil-POO's object surface does not expose all those inputs.

* Lean rewrite status

The Lean modules are separated by semantic responsibility:

- ~LeanPoo/C4/Types.lean~ owns named nodes, local parent orders, suffix flags,
  errors, and graph validation.
- ~LeanPoo/C4/Merge.lean~ owns the ordered C3 candidate merge used inside C4.
- ~LeanPoo/C4/Linearize.lean~ owns the C4 translation: parent precedence lists,
  inherited suffix selection, suffix-tail restriction, prefix merge, and final
  precedence list. It validates only the root's reachable inheritance graph;
  unrelated declarations do not affect that root. All loops are bounded by
  finite input sizes; no ~partial def~ is used.
- ~LeanPoo/Prototype/Compose.lean~ owns the open-recursive prototype type,
  identity, pairwise composition, and a type-indexed ~Chain~ for changing
  intermediate types. Lean proves identity, associativity, typed chain
  concatenation, and agreement between chain interpretation and composition.
  This realizes the POOF paper's composition laws and part of its hypothetical
  dependent type notation directly in Lean. Homogeneous list composition reuses that chain.
  ~instantiate~ and ~instantiateAll~
  provide the function-valued fixed point from ~proto.ss~.
- ~LeanPoo/Prototype/SlotSpec.lean~ owns the four semantic slot-spec forms and
  their single evaluator. Its delayed ~Method.compose~ is the one composition
  operation used to assemble inherited slot computations.
- ~LeanPoo/Object/Schema.lean~ gives slots dependent value types and keeps
  ordered direct slot/default entries as the only declaration source, separate
  from the C4 graph. One generic dependent ~Entry~ supplies typed lookup and
  ordered replacement for both entry kinds. ~fromValues~ and ~fromFunction~ translate the Gerbil
  direct-value and lazy-function constructors. ~fromValuesIndexed~ uses a
  hash-indexed array position to retain first-key order and last-value
  semantics for wide typed value streams, following Section 10's finite-map
  representation argument. ~fromMap~ accepts a typed
  dependent map and orders keys with a caller-supplied comparator.
  ~Entry.toMap_get?~ proves that materializing an ordered declaration list
  into a dependent hash map preserves last-write-wins lookup for every key.
- ~LeanPoo/Object/Builder.lean~ provides a Lean-native expression layer over
  those declarations. Its pure ~StateM~ programs compose with ~do~ notation;
  ~buildOn~ supports reuse, and reduction theorems connect the builder to the
  existing direct-value and inherited-method operations. A focused inherited
  update lifts a monomorphic lens through the same delayed method form;
  ~Builder.skew~ also lifts a general skew-focused open prototype into a C4
  slot, with final-self view and delayed inherited input. This follows the
  upstream separation between convenient expression and object semantics
  without translating Scheme macro syntax into Lean.
- ~LeanPoo/Prototype/SkewLens.lean~ implements the paper's distinction between
  the context viewed by a lens and the extension it updates. Identity and
  composition are proved associative. ~SkewLens.focus~ translates the paper's
  ~skew-ext~ onto the existing open ~Proto~, with a proof that focusing through
  composed lenses equals successive focusing. ~refocusUpdate~ narrows only
  the update target; a getter/setter pair supplies the monomorphic special
  case used by nested specification updates.
- ~Object.Lens.specification~ is the paper's prototype-specification focus for
  a validated C4 object. Its setter uses ~Memoized.reviseDeclaration~, which
  rebuilds the target from the new specification. Lean proves equivalence of
  lens modification with that revision and preservation of C4 precedence;
  there is no target-only update that could leave an extensible prototype out
  of sync with its specification.
- ~Declaration.withoutSlot~ and ~withoutDefault~ implement the paper's
  non-monotonic specification edits. ~Entry.erase~ preserves the order of all
  other direct entries and removes every write at the chosen key; Lean proves
  that the removed direct lookup is absent. ~Lens.directSlot~ and
  ~Lens.directDefault~ compose with ~Lens.specification~ to focus on one
  optional contribution. Removing a direct contribution leaves the full C4
  ancestor graph intact, so inherited methods and defaults can become visible.
- ~Object.Lens.mapError~ and ~modifyM~ make nested prototypes ordinary typed
  slot values with independent C4 plans. Error mapping permits lenses from
  independently defined layers to compose; a fallible inner extension must
  succeed before the outer declaration is rebuilt. Identity/composition of
  error mapping and its pure-update special case are proved in Lean.
- ~LeanPoo/Object/Resolve.lean~ assembles defaults and lazy inherited methods
  in C4 order, following ~object.ss~. ~compile~ creates a reusable C4 plan;
  ~resolve_compiled~ proves it agrees with the one-shot entry point. The
  executable ~Plan.resolve~ now accumulates methods from least to most
  specific, and ~Plan.resolve_eq_compileSlot~ proves equality with the
  original most-specific-first C4 fold for every key and open self. ~Plan.ref~
  reports a missing required slot explicitly.
- ~LeanPoo/Object/Indexed.lean~ indexes each declaration's defaults and slot
  methods in dependent hash maps. ~IndexedPlan~ carries an alignment proof;
  ~IndexedPlan.resolve_sound~ proves its resolver equals ~Plan.resolve~ for
  every key and open self. The construction uses ~Entry.toMap_get?~ and the
  same C4 parent-first fold.
- ~LeanPoo/Compose.lean~ exposes ~LeanPoo.mix~, ~LeanPoo.extend~, and
  ~LeanPoo.plus~, and ~LeanPoo.clone~ as immutable graph constructors that
  compile a C4 plan. They correspond to Gerbil's ~.mix~, ~.extend~, ~.+~,
  and ~.cc~. ~.+~ accepts the flat parent order exposed by Gerbil and rejects
  C++ multiple-order input. ~clone~ preserves the source node's topology and
  defaults, replaces only requested direct slots, and rejects duplicate keys.
- ~LeanPoo/Slots.lean~ exposes ~LeanPoo.hasSlot~, ~LeanPoo.allSlots~,
  and ~LeanPoo.prepareDeclared~. Enumeration follows the C4 chain from least
  to most specific and reads keys directly from the ordered declarations.
  Instance preparation, cache creation, and cache forcing can consume that
  same order without a caller-provided key list. ~collectValues~ handles
  caller-selected keys once; ~Object.Instance.values~ and ~Memoized.values~
  reuse it for the full declaration order.
- ~LeanPoo/Object/Memo.lean~ ties a lazy thunk table across declared keys.
  ~Plan.memoize~ builds an executable open-recursive object with one shared
  call-by-need cell per key; ~Memoized.values~ materializes its values.
  ~Plan.memoizeCompiled~ optionally assembles effective methods in one
  base-to-child pass before creating those cells, reflecting Gerbil-POO's
  ~compute-slot-funs!~. It uses the same ~SlotSpec.toMethod~ and
  ~Method.compose~ operations; ~CompiledMemo.lean~ checks representative
  behavior, including a C4 diamond. The forward-fold theorem proves the
  composition order; ~Entry.foldMap_get?_lookup~ and
  ~Declaration.compileLocalMethods_get?~ prove the local duplicate-slot
  normalization as direct ordered writes. ~compileTablesFor_default_get?~,
  ~compileTablesFor_method_getD~, and ~Plan.compiledTables_resolve~ prove
  cross-node resolution for every key and open self.
  ~Plan.compileEffective_get?_mem~ proves lookup for every materialized key.
  ~Plan.compileMemo~ packages the table and proof as a reusable ~CompiledPlan~;
  each ~CompiledPlan.instantiate~ allocates fresh lazy cells without rebuilding
  effective methods. This applies the source's staging distinction to repeated
  instances of one immutable topology and declaration set.
  ~Plan.memoizeIndexed~ has a
  general resolver soundness theorem and a different performance profile.
  The executable object's ~ResolutionMode~ keeps the chosen method-building
  strategy through derived
  objects and mutable revisions; mixing independent objects follows the left
  receiver's mode.
  ~Memoized.extend~, ~mix~, ~plus~, and ~clone~ keep the prototype and
  executable instance together while deriving a fresh object. ~Memoized.foldSlots~
  traverses typed values in declaration order. ~Schema.mergeDisjoint~ and
  ~Memoized.mixWith~ compose separate object families with explicit node-name
  collision reporting. ~reviseSlot~ and ~reviseDefault~ persistently update an
  existing prototype declaration, preserve C4 when topology is unchanged,
  and allocate a fresh lazy instance; ~force~ and ~valuesSorted~ cover eager materialization and sorted
  export.
- ~LeanPoo/Object/Prepare.lean~ stores preassembled, dependently typed slot
  functions in ~Std.DHashMap~ for selected keys. Each entry carries a proof
  that it computes the same value as ~Plan.resolve~.
- ~LeanPoo/Object/Cache.lean~ stores evaluated values in an explicit immutable
  cache. Its read operations return the updated cache, and the soundness
  theorems connect cached results back to the resolver. ~Cache.rebase~ carries
  entries to another resolver only with a proof of equal resolved values.
  ~peek~ inspects only cached values; an absent resolution does not insert an
  entry.
- ~LeanPoo/Prototype/Class.lean~ owns composable runtime descriptors and
  JSON/text/byte codecs. ~Types.lean~ adds heterogeneously typed tuples,
  descriptor/value pairs, fixed-width integers, integer ranges, and
  rationals using Lean's type system. A descriptor may supply a validated
  prototype value for a class slot.
- ~LeanPoo/Object/Generic.lean~ selects typed methods from instance slots or
  class/type descriptors. ~Class.lean~ maps typed slot rules to the existing
  declaration and C4 evaluator, including class inheritance and JSON object
  reconstruction. ~Lens.lean~ implements persistent slot get/set/modify.
- ~LeanPoo/Object/Instance.lean~ states the fixed-point equation for an open
  recursive object. Closed plans can be instantiated directly; instance
  preparation and caching share the validated plan and final self.
- ~LeanPoo/Object/Ranked.lean~ constructs a total fixed-point instance for
  plans whose resolved slots read self only at strictly smaller natural-number
  ranks. ~Dependencies.inferRanked~ schedules finite declared dependencies,
  identifies missing sources by reader and key, rejects blocked cycles, and
  checks every edge before producing the rank. ~Dependencies.instantiate~
  returns the proof-bearing instance directly.
  Its locality proof connects that well-founded evaluation to the ordinary C4
  resolver, including inherited declarations. The resulting instance uses the
  existing certificate and cache APIs.
- ~LeanPoo/Object/Incremental.lean~ computes a conservative reverse-dependency
  footprint from that schedule, checks closure, proves old and new instance
  values equal outside the footprint, and rebases only those cached entries.
  ~Dependencies.revise~ combines those steps into one checked update.
  ~Object.Debug.Revision.explainImpact~ reports the direct edit and affected
  reads without adding instrumentation to each slot.
- ~LeanPoo/Object/Lazy.lean~ allocates call-by-need cells from a proof-bearing
  total instance. Each cell carries its value equation; ~Revision.rebaseLazy~
  retains the same thunk for unaffected keys and creates fresh cells for
  affected keys, independently of the partial ~Plan.memoize~ fixed point.
- ~LeanPoo/Proof/Types.lean~, ~Patch.lean~, ~Batch.lean~, ~Reuse.lean~,
  ~Invalidation.lean~, ~Object.lean~, and ~Revision.lean~ own proof objects, append, right-side
  override, obligation transport, pending obligations, descendant
  invalidation, and certificates over typed object instances.
  ~Batch.lean~ folds typed patches and proves agreement with sequential append,
  exact touched-key order, last-write precedence, and the condition for
  reusing an obligation through every patch in the batch.
  ~Revision.lean~ projects a checked object update into the existing patch
  algebra, proves that applying it yields the new fixed point, and closes the
  certificate using only pending obligations.
- ~Justfile~ offers module-scoped compilation commands. ~just check~ builds
  the complete Lean library, executes the integrated examples, and parses
  every maintained Org page.

The C4 rewrite follows these source operations:

| C4-Mixins ~linearize.hpp~ | Lean translation |
|---------------------------+------------------|
| ~concat_unique_all_t<parent_orders>~ | ~parents~ |
| ~parent_precedence_lists_t~ | ~parentResults~ |
| ~merge_parent_suffixes_t~ | ~inheritedSuffix~ selection |
| ~suffix_tail_t~ and suffix order check | ~inheritedTail~ and ~respectsSuffixTail~ |
| ~remove_all_from_lists_t~ | ~withoutTail~ on candidate lists |
| ~c3_merge_t~ | ~merge~ |
| ~cons_t<Node, prefix ++ tail>~ | final ~precedence~ |

Lean evaluates the finite graph with bounded parent-first recursion and a
table of completed results instead of C++ template recursion. Each reachable
node's precedence is computed once; cycles exhaust the finite node-depth
bound. ~merge~ follows the C++ ancestor-counting update: count
candidate tails once and decrement counts when a selected head exposes a new
head. ~Std.HashMap~ stores both those counts and completed precedence lists;
~Std.HashSet~ handles duplicate detection and order-preserving deduplication.
The reachable subgraph is now discovered with a finite breadth-first queue
bounded by the source edge count. A first-declaration node index avoids
repeated name scans during discovery; validation still reports reachable
duplicate declarations before unknown parent references. Merge results and
parent results use reverse accumulation and reverse once at the boundary.
~just benchmark-c4~ measures deep chains and wide fan-in graphs, while
[[file:../Tests/C4Traversal.lean][C4Traversal.lean]] checks the reachable-error boundary.
The integrated example executes both a suffix-tail graph and multiple local
parent orders from C4-Mixins, as well as cycle and conflicting-order
rejection.

* Proof composition boundary

An obligation declares the keys on which its proposition depends and carries
a proof that equal values at those keys preserve it. A patch declares its
touched keys and proves that all other keys retain their values. ~Patch.set~
constructs the frame proof for a typed single-key override. ~reuse~ then
transports an existing certificate across an unaffected patch; ~closePending~
requires fresh proofs only for touched obligations and newly added ones.
~Patch.then~ applies patches in order, so the later patch receives the state
produced by the earlier one. ~mem_pending_iff~ proves that the executable
pending list selects exactly affected old obligations and new obligations.
~CertifiedObject.applyValues~ binds an ordered batch of typed overrides to
the next resolved instance, using the same certificate transport as
~applyPatch~. ~rebaseInstanceCache~ transports evaluated values outside the
patch footprint using the old and new instance equations and the patch frame
proof. ~rebaseInstanceCacheByValue~ compares stored values with the new
resolver, covering computed dependents without a supplied footprint and
without rerunning the old resolver; it can force the new instance.
~Proof.patchOfRevision~ derives a finite patch from a checked ~Object.Revision~.
Its alignment theorem covers keys outside the finite declaration support as
well as unaffected declared keys. ~CertifiedObject.applyRevision~ then uses
the existing pending-obligation and certificate machinery.
~invalidatedNodes~ follows reverse
inheritance edges for structure-level invalidation. Its step is monotone;
~Descendant~ indexes an inheritance path by edge count. Lean proves that
changed nodes remain in the result and that every descendant reachable within
the graph's finite propagation bound is selected. Conversely, every selected
node has such a path. ~mem_invalidated_iff_bounded_descendant~ is the exact
specification of the executable result for arbitrary graphs.
~C4.Graph.inferRanked~ now checks a finite whole-graph ancestry rank, with a
proof that every parent has smaller rank and every node rank is below the
node count. ~Descendant.rank_distance~ and ~within_graph_bound~ then bound
all inheritance paths. ~mem_invalidated_iff_descendant~ characterizes the
result by reachability without a caller-supplied path bound, and
~mem_impactStep_invalidated_iff~ proves closure after the finite pass.
~Proof.certifyInvalidation~ returns this executable list together with its
exact reachability proof, rejecting malformed or cyclic whole schemas.
Parent-edge acyclicity is independent of C4 method-order and suffix
constraints; the existing linearizer still checks those constraints.
Whole-schema rank checking includes branches outside one root's ancestry.
It does not extract a global rank merely from success of the root-local C4
linearizer. Structural impact does not inspect dependencies hidden in slot
functions or implement a whole-heap instance migration policy.

~Object.Instance~ states the self equation for a validated compiled plan, and
~CertifiedObject~ binds its obligation certificate to that instance. The
~CertifiedObject.applyPatch~ operation accepts a C4-valid next instance,
checks that its state is the patch result, and uses ~closePending~ to assemble
the new certificate from reused and newly discharged obligations. The
library constructs closed instances with ~Object.Closed.instantiate~ and
executes general open recursion with ~Plan.memoize~. The executable thunk
knot is partial, so it does not by itself provide the equation required by
~Object.Instance~; proof-bearing clients supply that equation explicitly or
construct it from ~Object.Ranked~ for well-founded dependencies. No
concrete policy semantics domain is part of this repository yet.

Section 6's class-redefinition exercise now has an explicit per-instance
snapshot migration protocol in ~Object.Migration~. Transfers preserve equal
payload types across renaming or invoke a typed, fallible conversion. The new
class supplies defaults and computed fields; omitted old fields survive only
in the old snapshot. ~ClassSpec.migrateFrom~ returns a new object together
with its class-acceptance proof. This covers the exercise's four field
operations, without a live-instance registry or persistent-store index upgrade.

The next section 6 exercise has three explicit update policies in
~Mutable.reviseWithPolicy~: eager forcing before installation, lazy fresh
cells, and versioned fresh cells plus an old-specification handle. The tests
compare their missing-target behavior and snapshot consistency under all
three resolver modes. This is a finite per-instance protocol; it does not
implement process suspension or a native code loader.

The following section 6 exercise now has a cooperative quiescent-upgrade
protocol in ~Object.Upgrade~. Erlang's
[[https://www.erlang.org/doc/system/code_loading.html][code replacement documentation]] describes current and old module code;
fully qualified calls select current code while old calls may continue.
[[https://www.erlang.org/doc/apps/stdlib/sys.html#change_code/5][sys:change_code]] requires a suspended process and invokes its state-change
callback. [[https://www.erlang.org/doc/apps/kernel/code.html#soft_purge/1][code:soft_purge]] refuses to remove old code while processes still linger
in it. These mechanisms separate switching versions, state conversion, and
retiring executable code.

LeanPoo's simplifying design separates operation admission from execution:
pause rejects new operations; already admitted callbacks retain their captured
specification; commit requires all such callbacks to exit. A mutex guards the
control state and publication. Version plus request number rejects canceled
or completed sessions, and a pure updater supplies data conversion.
The ~Control.commit_quiescent~, ~commit_authorized~, and ~enter_paused~ laws
are kernel-checked; tests use two real readers whose completion is controlled
by promises. The Person example composes the boundary with typed class
migration. Stack-held objects remain immutable old snapshots after upgrade;
there is no inspection, rewriting, or purging of native call stacks or code.
The guarantee covers scoped operations on one runtime, with joined background
work and a fixed Lean key/value family. It does not implement Erlang process
suspension, release supervision, native module loading, or heap-wide upgrade.

Section 7's research exercise on two-level inheritance now has an explicit
C4-based construction in ~Object.SortedInheritance~. A selected sort hierarchy
provides priority; a complete finite classification assigns each selected
specification to one sort. Cross-sort pairs are installed into the applicable
ancestry orders before the final wrapper is compiled. Existing local orders
and suffix constraints can reject the policy. The returned certificate checks
the actual C4 precedence; ~requirements_complete~ and ~higher_precedes~ prove
complete coverage and ordering of every higher/lower selected pair. Tests
cover noncommuting methods, same-sort ties, all resolver modes, typed function
slots, future reclassification, and hierarchy/local/suffix conflicts. This
construction uses explicit metadata and enumerates candidate pairs; it does
not infer categories from opaque methods or establish an ~O(nd)~ bound.

Section 7's extended-precedence discussion now has an operational formalization
in ~C4.Precedence~. Eligibility is defined independently by absence from all
candidate tails; selection chooses the first eligible head. ~choose_eligible~
and ~choose_leftmost~ prove feasibility and rejection of all earlier heads.
An inductive ~Trace~ records each choice and complete termination, and
~Trace.unique~ proves that two accepted traces for the same input agree.
~mergeCertified~ replays the optimized tail-count merger's output using this
independent structural definition. ~linearizeChecked~ opts into this replay at
every reachable node's prefix merge. Suffix members are excluded before the
choice and retained for final append; ~candidates_without_suffix~ proves
reduction to ordinary C3 candidate construction when the suffix is empty.
This formalizes the paper's operational tie rule. It does not prove the whole
optimized algorithm correct for every graph, nor equivalence to Ducournau's
original extended-precedence graph relation.

The paper's ordered-subset formulation of monotonicity now has a merge-level
law: ~Trace.preserves~ proves that every input candidate is a ~List.Sublist~
of the completed output. This covers both inherited parent precedence and
local-order candidates. ~Trace.covers~ proves exact name coverage, and
~Trace.nodup~ proves that the output contains no repeated names, even when
different candidates share ancestors. These laws apply to every complete
trace and therefore every ~Certified~ result. They do not assume a bounded
graph size or a particular fixture.

~C4.Suffix~ connects the prefix proof to complete ancestry. The runtime
~respectsSuffixTail~ check implies a split into a suffix-free prefix and an
ordered sublist of the inherited tail. ~append_preserves~ proves that the
complete original order survives prefix merging and tail append.
~mergeWithSuffixCertified~ checks this split for every complete parent and
local order and returns a ~SuffixCertified~ result: input-order preservation,
exact input-or-tail coverage, and actual tail suffix retention. Its no-duplicate
law assumes the caller's tail has no duplicates. ~linearizeChecked~ now uses
these full-ancestry certificates at every reachable node.

~C4.NodeCertificate~ adds independent validation of the graph computation's
selected tail against the actual cached parent tails. ~TailCertified~ requires
selection from those inputs (or empty selection for no inputs) and every input
to be a literal suffix of the selected tail. Its ~longest~ and ~unique~ laws
prove maximal length and unique selection; ~comparable~ proves that the input
tails form a total suffix order. ~NodeCertified~ checks that the
tail is duplicate-free and the node name is absent from the reconstructed
ancestry. Its full output preserves each parent/local order, retains each
parent tail as a suffix, contains no repeated names, and starts with the node
name. ~linearizeChecked~ constructs this certificate at every computed node.
These are general laws over the supplied orders and cached tails.

~C4.GraphCertificate~ now provides a separate graph-derived certificate for
the ordinary compiler's exact returned list. ~GraphTrace~ binds every node
to its first declaration lookup in the original graph, records every declared
parent edge, and recursively supplies the parent derivations used to construct
that node's orders and tails. ~GraphCertified~ carries both this trace and an
equality to ~linearize graph root~. Its laws establish duplicate-free output,
root-first order, exact reflexive ancestry coverage, transitive ancestor-order
preservation, local-order preservation, and actual suffix retention for any
graph ancestor declared as a suffix. Two accepted certificates for the same
graph/root agree about output.
~linearizeCertified~ reconstructs independently from graph declarations and
rejects a mismatch with the ordinary compiler. It does not trust the compiler's
cached metadata. The public independent ~reconstruct~ path now succeeds
exactly when the root admits a finite ~GraphTrace~, reproducing its complete
precedence and most-specific tail within ~graph.nodes.length~ steps of depth.
~GraphTrace.unique~ proves both lists are fixed by the original graph.
Completeness of the ordinary optimized traversal and equivalence with
Ducournau's original relation remain open. Verification can repeat shared parent work; no efficiency bound
is claimed for this path.

The structural reference merger ~Precedence.mergeReference~ now has a
completeness theorem: whenever a finite ~Trace lists output~ exists, the
merger succeeds with exactly that output. ~Trace.length_bound~ proves that
the candidate-position count is sufficient fuel; ~mergeReference_success_iff~
characterizes success exactly by existence of a complete operational trace.
This theorem does not assume correctness of the optimized tail-count state.
Independent graph reconstruction now uses ~certifyNodeReference~ and this
structural merger. ~GraphTrace.declared~ and ~GraphTrace.length_bound~ bind
all output names to original declarations and bound output size by graph size;
~GraphTrace.parent_budget~ proves strict output-length decrease along a parent
edge. The reconstruction completeness proof now combines these bounds with
suffix-check completeness for duplicate-free tails, exact reproduction of a
certified longest tail, and reference node reconstruction completeness.
~linearizeCertified_complete~ proves certification succeeds whenever the
ordinary compiler has returned an output admitting a ~GraphTrace~.
Existence of a ~GraphTrace~ is the explicit consistency criterion here; its
equivalence to the paper's original relation remains unproved. Optimized
candidate merging now has its own soundness and completeness proof below;
ordinary graph traversal completeness remains open.

The optimized ~C4.merge~ now has a simulation proof in ~C4.MergeInvariant~.
~CountInvariant~ counts every occurrence in the actual candidate tails.
Initialization, newly exposed-head accounting, incremental decrement, empty
candidate pruning, head selection, and the finite fold all preserve the
structural merge semantics. ~merge_sound~ derives a complete ~Trace~ from
any actual successful raw result; ~merge_complete~ reproduces every complete
trace with the runtime's original candidate-position budget.
~merge_reference_output~ equates optimized/reference successful outputs and
rejection domains for arbitrary finite candidates. The independent checker
and optimized certified merger are also complete. This closes the optimized
candidate-merge state invariant; it does not close the ordinary graph
traversal's ancestry/suffix cache invariant or establish a complexity bound.

The ordinary compiler now exposes named runtime operations in
~C4.LinearizeState~ for the next traversal proof. ~nodeIndex_lookup~ equates
its first-write HashMap with the original graph's first declaration lookup.
The actual inherited-suffix walk is sound for finite pointer paths with any
budget. Under a literal-suffix cache-link invariant, link lengths strictly
decrease, visited sources are distinct actual keys, and ~table.size + 1~ is
proved sufficient. Its acceptance then exactly matches finite pointer
reachability and retains complete target precedence as a literal suffix.
~CacheInvariant~ binds cached complete precedence to ~GraphTrace~;
fresh insertion preserves this property when the new result provides its
derivation and link evidence. A successful walk through such a cache witnesses
original-graph ancestry. These laws do not yet prove that ~computeNode~ or
~resolveNode~ populate a valid cache, nor that ~mostSpecificSuffix~ selection
matches a graph trace. The ordinary graph compiler's completeness remains open.

* Paper-derived boundaries

The [[https://fare.tunes.org/files/cs/poof.pdf][POOF paper]] gives the constructive object model, not the
~ProofObject~ / ~Patch~ / ~Certificate~ interface. Its section 1 identifies
prototype composition as an associative operation with an identity; Lean's
~Prototype.compose~ and typed chain have those laws. Sections 4.2 and 4.3
pair an instance with its reusable prototype and compute an inheritance
order; ~Memoized~ retains the compiled plan with the lazy instance, while
the separate C4 source supplies this project's ordering algorithm. Section
5 derives classes from prototypes for type descriptors; Lean's descriptor
and class layers use native types rather than Scheme's dynamic MOP.

For the certified finite-dependency path, ~Object.LazyInstance~ also retains
actual thunk cells across a revision. The table's ~Memoized~ limitation refers

~Proof.Runtime~ binds those cells and the explicit value cache to one
certified instance. Its revision carries both forms of sound reuse into the
next runtime before ~MutableRuntime~ installs it. This is a declared finite
dependency policy, not automatic tracking of arbitrary Lean computations;
the paper notes that universally correct automatic mutation tracking would
need to cover the wider language, beyond the object system.
The paper also calls out precedence lists as an expensive computation worth
retaining. Declaration-only edits now reuse ~Plan.valid~ and its C4 order;
ordered batches allocate a single new executable instance and install it only
after every edit succeeds. Structural edits still recompile C4. This separates
topology reuse from value-cache invalidation.
Section 10's method-caching exercise suggests eight recently used generic
shapes and four at a dynamic call site. ~ShapeCache~ now bounds the generic
candidate and prepared effective-method caches to eight shapes; ~InlineDispatch~
holds four proof-bearing call-site entries. Candidate predicates remain
value-sensitive after either cache hit, and registration clears caches in
the new immutable dispatch value.
The paper's optional runtime descriptors and future method-combination
mechanisms are not a conformance checklist for Lean's static type system.

Section 10's suffix access now retains the introducing specification and its
position in the least-specific-first suffix-ancestor vector. A fast read
checks that ancestry position and the field offset; a foreign same-name field
falls back to ordinary keyed reading.
Section 10 also describes small per-site field-offset caches and a cache
shared by sites reading the same field name. ~PolySlotAccessSite~ retains four
offsets, while ~SharedSlotOffsets~ retains eight learned offsets per name.
Local entries pair a layout fingerprint with an offset, and a hit allocates no
updated cache. A fingerprint collision still checks the actual field. Local
hits do not write the shared cache. Every speculative
offset is checked against the current layout before a lazy cell is read; a
miss falls back to ordinary keyed lookup and teaches both levels. The
~read_sound~ theorem states equality with ordinary object reads, including
after a layout change or an absent field. ~just benchmark-layout~ measures
single-layout and alternating-layout access separately.

* Further C4 closure: executable suffix selection

The runtime parent-suffix selector now has kernel proofs for input retention
and domination through actual inherited-suffix pointers. A valid cache and
pairwise comparable supplied pointer chains suffice for successful bounded
selection. Given the selected cached entry, the result constructs the
independent ~TailCertified~ used by complete node checking.
The optimized suffix and node checkers also reproduce arbitrary supplied
certificates, connecting optimized merge completeness to the full node
checker. This advances the implementation proof connection; it does not
establish the selector's canonical metadata premises from the original graph.
The next obligations are parent collection/deduplication, canonical suffix
metadata, and cache population by ~computeNode~ and ~resolveNode~.
