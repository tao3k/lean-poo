#+TITLE: Reusable API contracts

This guide starts from application tasks and the guarantees clients can use.
The generic Lean snippets are compiled in [[file:../Tests/ReusableContracts.lean][ReusableContracts]].
[[file:../Examples/README.org][Examples]] shows complete scenarios; this page explains how to choose and
combine reusable library interfaces.

* Choose the compilation result

| Need | Interface | Contract and cost |
|------+-----------+-------------------|
| An executable precedence | ~C4.linearize~ | Source-shaped finite compiler; returns ~Except Error (List String)~; suffix crossing can reorder an ancestor's local constraint. |
| Independent checks at each reachable node | ~C4.linearizeChecked~ | Successful output has an original ~GraphTrace~, by ~linearizeChecked_graph_sound~. |
| Retain that result with proofs for client code | ~C4.linearizeVerified~ | One checked compilation; returns ~VerifiedOrder graph root~. Proof fields erase at runtime. |
| Repeated ancestry queries | ~order.indexAncestors~ | One hash-set construction from the retained order, followed by hash-set queries. |
| Independent full graph reconstruction | ~C4.linearizeCertified~ | Ordinary compilation plus separate reconstruction; shared parent work may repeat. |

~linearizeVerified_projection~ proves exact output and error preservation
relative to ~linearizeChecked~. The new wrapper does not independently replay
the graph a second time. It validates the root's reachable declarations;
unreachable duplicate names or missing references do not become global schema
errors. None of these interfaces proves equivalence with the original
Ducournau relation. Ordinary-to-checked acceptance fails in general: the
[[file:reference-study.org::*Suffix crossing and the stronger graph contract][suffix-crossing study]] records a five-node counterexample. Use
~linearizeVerified~ when the application relies on complete ancestor-order
preservation.

* Audit an ordinary node already computed from canonical parents

Advanced clients retaining a resolver cache can use
~LinearizeState.computeAuditedNode table node~. It executes one ordinary node
merge and audits the result's uniqueness and complete parent-order
compatibility. It returns ~AuditedNode table node~, retaining the exact
ordinary execution and audit receipts. Its proof fields erase at runtime.
The audit reads parent/suffix metadata and scans the orders; it invokes no
merger. No measured speedup is claimed.

Supply ~valid : MetadataInvariant graph table~ to ~receipt.checked~ to prove
exact checked acceptance without executing checked again. With the original
node lookup ~found~, ~receipt.graphSound valid found~ recovers ~GraphTrace~:

#+begin_src lean
example (receipt : LinearizeState.AuditedNode table node)
    (valid : LinearizeState.MetadataInvariant graph table)
    (found : graph.findNode? node.name = some node) :
    GraphTrace graph node.name receipt.result.precedence
      (if node.suffix then receipt.result.precedence else
        LinearizeState.selectedTail table receipt.result.inheritedSuffix) :=
  receipt.graphSound valid found
#+end_src

~receipt.insertSound valid found fresh~ preserves canonical metadata when
inserting at a fresh node name. Starting with an arbitrary raw cache requires
its own metadata proof. An audit of an invented result is insufficient;
the retained ordinary execution receipt binds the proof to the actual result.

~computeNode_checked_iff~ characterizes single-node acceptance on canonical
parents: ordinary success, duplicate-free output, and ~ParentCompatible~
are necessary and sufficient. ~auditNode_acceptance_iff~ characterizes the
executable audit when the exact ordinary success is supplied. Audit errors
are its own diagnostics; this does not assert complete error-payload equality
with checked mode.

* Compile a whole graph through ordinary computation and audits

~linearizeAudited graph root~ resolves parents recursively from an empty cache.
Each fresh node executes ordinary computation once, followed by its audit;
shared ancestors use the retained cache. Validation, reachability, cache hits,
and fuel follow the existing resolver. No checked compiler is executed by this
API. The audit still reads and scans metadata; no measured speedup is claimed.

Successful execution establishes an original ~GraphTrace~ without caller
compatibility, metadata, or trace premises:

#+begin_src lean
example (success : linearizeAudited graph root = .ok output) :
    ∃ tail, GraphTrace graph root output tail := linearizeAudited_graph_sound success
#+end_src

~linearizeAudited_accepts_mode success true~ proves checked acceptance of the
same output; ~linearizeAudited_ordinary success~ proves ordinary acceptance.
For an advanced client starting from a canonical cache,
~resolveAuditedNode_acceptance valid success~ supplies both exact resolver
successes and the final ~MetadataInvariant~. These are successful-execution
contracts; complete error-payload equivalence is not claimed.

~resolveAuditedNode_success_iff valid~ supplies the converse as well: checked
recursion on the same canonical cache and fuel succeeds exactly when audited
recursion returns that same cache. Cached zero-fuel hits are included.

Use ~linearizeAuditedVerified graph root~ to retain a ~VerifiedOrder~ with all
existing ancestry, hash-index, ancestor-order, and suffix contracts. It runs
the audited compiler and uses erased proofs to supply checked acceptance;
it does not rerun checked compilation. Its projection theorem preserves the
audited compiler's output or error exactly. ~linearizeVerified~ continues to
provide the checked compiler and its exact diagnostics.

The ordinary compiler alone still accepts the demonstrated suffix-crossing
counterexample. The audit rejects it. A successful audited execution closes
the graph soundness path for this API, without asserting unrestricted ordinary
soundness or measured performance gains.

* Interchange audited and checked successful results

~linearizeAudited_success_iff~ proves exact success equivalence for every graph,
root, and output, without caller validity premises. A client that already has
a checked execution receipt can transfer it directly:

#+begin_src lean
example (checked : linearizeChecked graph root = .ok output) :
    linearizeAudited graph root = .ok output := linearizeAudited_checked_complete checked
#+end_src

For clients intentionally discarding failure diagnostics,
~linearizeAudited_toOption~ proves the two optional outputs equal.
The same guarantee is available after retaining a ~VerifiedOrder~:

#+begin_src lean
example : ((linearizeAuditedVerified graph root).map (·.output)).toOption =
    (linearizeChecked graph root).toOption := linearizeAuditedVerified_toOption
#+end_src

Thus choosing ordinary computation plus audits loses no checked successful
input or output. On failure, retain the original ~Except~ value if the specific
diagnostic matters: these theorems do not equate error payloads. No performance
improvement follows from success equivalence alone.

* Retain failure receipts and prove the rejection boundary

~diagnoseAudited graph root~ executes audited compilation once and returns
~Except (RejectedOrder graph root) (VerifiedOrder graph root)~. On success,
retain the existing verified queries. On failure, ~receipt.error~ is the actual
audited diagnostic and ~receipt.rejected~ retains its execution equality.
Proof fields erase. ~diagnoseAudited_projection~ recovers the original audited
output or error exactly, so this wrapper does not rewrite diagnostics.

A rejection always excludes successful verified compilation:

#+begin_src lean
example (receipt : RejectedOrder graph root) : ¬ Nonempty (VerifiedOrder graph root) :=
  receipt.noVerified
#+end_src

~receipt.checkedRejected~ supplies checked rejection, with an existential
error rather than an equal error payload. A seven-node executable witness
combines contradictory prefix orders and a complete-parent suffix crossing:
audited reports ~inconsistentOrder~ while checked reports
~suffixOrderViolation~. Their successful-output equivalence does not imply
identical diagnostic priority.

To conclude there is no original finite graph derivation, supply reachable
declaration uniqueness. A common stronger input is global name uniqueness:

#+begin_src lean
example (receipt : RejectedOrder graph root) (unique : (graph.nodes.map Node.name).Nodup) :
    ¬ ∃ output tail, GraphTrace graph root output tail :=
  receipt.noGraphTrace (LinearizeState.reachableUnique_of_global unique)
#+end_src

~linearizeAudited_graph_iff unique~ characterizes successful execution by
original graph evidence; ~linearizeAudited_rejection_iff unique~ characterizes
failure by absence of any such evidence. The uniqueness premise matters:
two identical leaf declarations admit a kernel ~GraphTrace~ via first lookup,
but validation rejects the duplicate. Preserve ~receipt.error~ when explaining
validation failures to users; do not label every rejection as absence of graph
evidence without the required premise.

* Compile once, answer graph questions later

Retain ~order : VerifiedOrder graph root~ after successful compilation.
~order.head~, ~nodup~, ~length_bound~, and ~compiled~ expose the head,
uniqueness, graph-size bound, and equality with the ordinary compiler.
~covers~ proves exact ancestry membership, including the root itself.

For occasional queries, ~order.isAncestor query~ scans the retained list.
For many queries, retain ~index := order.indexAncestors~ and use
~index.isAncestor query~. Both return a Boolean with an ~isAncestor_iff~
theorem. Neither needs another compilation or graph traversal.

#+begin_src lean
example (order : VerifiedOrder graph root) (query : String)
    (present : order.indexAncestors.isAncestor query = true) : Ancestor graph query root :=
  order.indexAncestors.isAncestor_iff.mp present
#+end_src

For a constraint declared by a reachable ancestor, use
~order.ancestor_local_order path found declared~. It proves that the ancestor's
original local order remains an ordered sublist of the retained root output.
An indexed membership receipt supplies ~path~ directly:

#+begin_src lean
example (order : VerifiedOrder graph root) (query : String)
    (present : order.indexAncestors.isAncestor query = true)
    (found : graph.findNode? query = some node) (declared : constraint ∈ node.parentOrders) :
    constraint.Sublist order.output :=
  order.ancestor_local_order (order.indexAncestors.isAncestor_iff.mp present) found declared
#+end_src

Retain ~index := order.indexAncestors~ for repeated membership queries. This
proof consumes existing evidence; it does not compile each ancestor again.

~index.decideAncestor query~ supplies ~Decidable (Ancestor graph query root)~.
Install it with a local ~letI~ when a conditional needs a proof in its true or
false branch. This decision follows the executable hash query; it does not
introduce a classical, noncomputable decision procedure.

* Query precedence and reuse its proof

Import ~LeanPoo.C4.OrderRelation~ and retain ~order : VerifiedOrder graph root~.
~order.precedes left right~ answers whether the first name occurs before the
second in this exact retained result. It scans the list once, without another
compilation or graph traversal. It is not a hash lookup; no timing improvement
is claimed. Missing names and self comparison return ~false~.

~precedes_iff~ turns a true query into ~Precedes order.output left right~,
an ordered two-element sublist. ~precedes_members~ proves that both names are
original graph ancestors. For a resolver or handler pipeline, this lets a
consumer require an earlier provider and retain the proof alongside selection.

To reuse an ancestor's comparison in a descendant on the same graph:

#+begin_src lean
example (order : VerifiedOrder graph root)
    (ancestorOrder : VerifiedOrder graph ancestor) (path : Ancestor graph ancestor root)
    (before : ancestorOrder.precedes left right = true) : order.precedes left right = true :=
  order.monotone_precedes ancestorOrder path before
#+end_src

The caller supplies two retained results, not fresh compilation executions.
The theorem uses uniqueness of their original graph derivations to identify
the ancestor result, then transports its comparison through the root's
ancestor sublist. This does not transport an order across an edited graph.

~order.local_precedes path found declared before~ transports a pair from any
reachable declaration's original constraint. ~order.inheritance_precedes~
places a reachable node before each distinct ancestor of that node:

#+begin_src lean
example (order : VerifiedOrder graph root) (reachable : Ancestor graph node root)
    (path : Ancestor graph base node) (different : base ≠ node) :
    order.precedes node base = true := order.inheritance_precedes reachable path different
#+end_src

These apply to verified checked or audited results, including retained suffix
orders. They do not certify arbitrary ordinary compiler outputs. The
[[file:reference-study.org::*Paper properties and retained order relations][paper correspondence table]] separates these order contracts from the
still-open extended precedence graph and shape-isomorphism claims.

* Move a verified order into a new name space

Import ~LeanPoo.C4.Renaming~. Use ~graph.rename rename~ when composing independently
named resolver or factory families. It maps declaration names and every parent
reference, retaining declaration order, local-row order, and suffix flags.
It does not rename application provider dictionaries or change their values;
clients must align those keys with the renamed graph.

Retain the compiled order and supply an injective name map plus global
uniqueness of the original declaration names:

#+begin_src lean
example (order : VerifiedOrder graph root) (rename : String → String)
    (injective : Function.Injective rename) (unique : (graph.nodes.map Node.name).Nodup) :
    VerifiedOrder (graph.rename rename) (rename root) := order.rename rename injective unique
#+end_src

~order.rename~ maps its output list once. Its acceptance and graph proofs erase;
it does not execute either compiler, reconstruct parents, or run an audit.
The caller must use the same function for the graph, root, and queries.
For a fixed prefix, ~fun name => prefix ++ name~ is injective by
~String.append_right_inj prefix~. Distinct prefixes alone do not prove disjointness
of arbitrary preexisting family keys; establish that separately before union.
No runtime speedup is claimed.

~rename_output~ proves the exact mapped output. ~rename_unique~ identifies any
independently compiled verified result of that renamed graph with the migrated
one. Queries also commute with the mapping, even for self or absent names:

#+begin_src lean
example (order : VerifiedOrder graph root) (rename : String → String)
    (injective : Function.Injective rename) (unique : (graph.nodes.map Node.name).Nodup) :
    (order.rename rename injective unique).precedes (rename left) (rename right) =
      order.precedes left right := order.rename_precedes rename injective unique
#+end_src

Global declaration uniqueness is a sufficient explicit premise for this
consumer operation. Existing verified compilation validates only reachable
names, so a retained result alone does not discharge that stronger premise.
A collapsing map cannot supply injectivity and may cause duplicate-declaration
validation failure. This API transports C4 orders; it is distinct from the
object-slot ~Object.Renaming~ interface.

* Preserve caller ordering and inherited tails

~order.local_order~ transports a declared root constraint into the actual
returned precedence. ~order.ancestor_order~ supplies an ancestor's complete
derived order as a sublist. ~order.ancestor_suffix~ strengthens this to a
literal suffix for an ancestor declared with ~suffix := true~.

#+begin_src lean
example (order : VerifiedOrder graph root) (found : graph.findNode? root = some node)
    (declared : constraint ∈ node.parentOrders) : constraint.Sublist order.output :=
  order.local_order found declared
#+end_src

These proofs refer to exact original declarations and every original parent
edge, even when runtime normalization removes repeated edges and empty rows.
Applications can use them for ordered handler families, resolver pipelines,
or inherited specifications without reproving the C4 merge algorithm.

* Assemble context-dependent mathematical factories

Import ~LeanPoo.Functional.Assembly~. A ~Factory Context Result~ is
~(context : Context) → Result context~. A ~Provider Context Key Value~
maps a typed capability key to an optional factory. The result type can
include data and witnesses depending on the supplied context.

~Functional.assemble order providers~ chooses the first provided factory for
each key in the verified precedence. Selection returns function values; it
does not invoke factories. Resolve a capability once, retain that function,
and apply it to each context where its type permits. Missing capabilities
remain ~none~. ~assemble_origin~ proves the selected provider is an original
graph ancestor. ~apply_selected~ proves application uses the exact selected
function and supplied context.

Use one ~Context~ for mutually dependent source data, radius choices, and
their proof witnesses. Give the value family the type ~Context → Key → Type~.
If changing a parameter changes the required theorem, the factory must supply
the witness at the new indexed type. C4 selection supplies precedence and
provider provenance; the mathematical contract comes from this result type.
It does not automatically transport proofs across changed data.

For a required capability, use ~Functional.require provider key~ during
preparation. Match its ~Except~ once: ~.error key~ identifies the missing
capability and ~.ok build~ supplies a retained factory. Later calls to
~build context~ perform no provider lookup. ~require_ok_iff~ turns a successful
preparation receipt into ~provider key = some build~; combine it with
~assemble_origin~ to recover the original graph provider.

~Factory.zipWith combine left right~ invokes retained factories at the same
context and passes their data and witnesses to ~combine~. The result may be
a client's dependent record. ~Factory.reindex project build~ adapts a factory
to a larger context; the result is ~Result (project outer)~, preserving its
exact dependency. Supplying a fixed old witness where a new context requires
a different witness is still rejected by Lean.

The [[file:use-cases/navier-stokes-euler.org][Euler budget study]] identifies actual upstream factory call sites.
[[file:../Examples/ContextualFactories.lean][ContextualFactories]] shows the provider boundary with arbitrary
context-indexed mathematical types, a residual-only override, and a
~Prepared~ consumer retaining its required background/residual functions.
The external Euler repository supplies design references; no import or
build dependency is introduced.

* Prepare a typed capability checklist once

Import ~LeanPoo.Functional.Requirements~. Declare the capabilities needed by
one consumer as a ~List Key~. ~Requirements.prepare provider keys~ returns
~Except Key (Requirements.Factories Context Value keys)~. The tuple follows
the caller's key order; each component has its own context-indexed result
type. Empty lists succeed, and repeated keys retain repeated selected functions.
The first missing key is reported before any factory is invoked.

After matching success once, retain the tuple and call
~Requirements.build (keys := requested) retained context~ for every compatible
context, where ~requested~ is the checklist used for preparation. It returns
~Requirements.Results Value context keys~, a heterogeneous tuple indexed by
exactly that context and checklist. The builder adds no provider lookup or graph compilation; supplied factory
bodies keep their own behavior. Pass the results to your existing constructor; mathematical guards
and witnesses remain part of its own types.

~prepare_ok_iff~ proves the tuple's ~Selected~ contract: every component is
exactly the provider's selected function. ~Selected.available~ exposes this
for any requested key. ~prepare_origin~ combines it with a verified C4 order
and proves original-graph ancestry for every requested capability. These
contracts are generic over arbitrary key and context/result types.

[[file:../Examples/ContextualFactories.lean][ContextualFactories.Prepared]] now uses this library tuple instead of a
consumer-owned preparation record and repeated ~require~ statements. Changing
the checklist changes its type as well; adapt the consumer's constructor to
the new fields. This API removes repeated preparation plumbing, not the
consumer's domain-specific construction or analytic proof obligations.

* Preserve selected factories across provider-family renaming

~Functional.select_rename~ equates selection on mapped names when each mapped
provider agrees with the original provider on the requested key. Agreement is
needed only on the retained precedence. ~assemble_rename~ lifts that contract
to ~VerifiedOrder.rename~: supply the injective map, original global declaration
uniqueness, and provider agreement on original graph ancestors.

Graph renaming alone cannot rename a String-indexed provider dictionary.
Store the same factory values under the new names. If that alignment is
missing, selection can return a missing capability or a different factory;
the theorem requires the alignment explicitly. Capability keys and mathematical
contexts do not change. With it, selected functions agree exactly, so the
existing requirement tuple and consumer proofs remain reusable.

[[file:../Tests/FunctionalRequirements.lean][FunctionalRequirements]] compiles both generic provenance and renaming
clients, checks 192 preparation cases with heterogeneous result types, and
checks an aligned namespace prefix against independently compiled renamed
C4 output. A deliberately unaligned dictionary fails preparation.

* Reuse proofs after an unrelated change

~Proof.Obligation~ declares a predicate and the dependencies sufficient to
transport its proof. ~Patch.frame~ proves that untouched keys retain their
values. ~Proof.reuse~ combines those existing contracts:

#+begin_src lean
example (current : ProofObject Key Value) (update : Patch Key Value)
    (certificate : Certificate current) (obligation : Obligation Key Value)
    (owned : obligation ∈ current.obligations) (safe : unaffected obligation update) :
    obligation.holds (append current update).state :=
  reuse current update certificate obligation owned safe
#+end_src

~Proof.close~ builds the next certificate from the old certificate plus
proofs for affected old obligations and newly added obligations. The stability
and dependency contracts are premises, not facts inferred from a function's
source code. A change to viscosity, geometry, or forcing may affect many
obligations and cannot be certified as unrelated merely by choosing a new
provider name.

For several writes, ~Patch.setMany~ preserves dependent key types and uses
last-write semantics. ~Patch.setMany_last~ exposes that guarantee.
~CertifiedObject.applyRevision~ connects this proof workflow to the object's
checked finite change footprint when the caller supplies its resolver
alignment and discharges the pending obligations.


* Keep a prepared checklist stable across unrelated edits

~Requirements.prepare_congr provider other keys same~ proves exact equality
of preparation results when the providers agree on the requested keys.
Unrequested keys require no agreement. Both retained function tuples and
first-missing errors are preserved. This is a contract about provider values;
it does not inspect arbitrary factory bodies to infer their stability.

~Requirements.prepare_rename~ preserves the whole checklist through verified
graph renaming, with alignment needed only on requested keys at original
ancestors. It combines ~assemble_rename~ with ~prepare_congr~ and preserves
errors as well as successes. Namespace alignment remains a caller obligation.

* Access prepared factories by typed key

Import ~LeanPoo.Functional.Access~ and derive or supply ~DecidableEq Key~.
After a successful preparation, use
~Requirements.factoryAt (keys := requested) retained key member~. The proof
~member : key ∈ requested~ excludes a missing key and the return type is the
factory for that exact key. Literal lists usually discharge membership with
~by simp [requested]~. Repeated keys use their first tuple occurrence.

Retain this returned function before repeated context calls. Named access
scans the checklist; it is not a constant-time field offset. It invokes no
factory during the scan, and subsequent calls invoke the retained factory's
own body. A consumer no longer embeds positions such as ~.2.2.1~.

~factoryAt_selected~ gives ~provider key = some (factoryAt ...)~ from the
selected-tuple contract. ~factoryAt_stable~ proves named factory equality for
any two successful checklists from that provider containing the key. A newly
missing required key can still fail preparation. ~factoryAt_origin~ exposes
the exact original C4 ancestor supplying this function after verified assembly.

[[file:../Examples/ContextualFactories.lean][ContextualFactories.Prepared.build]] now extracts background and residual
by key, then retains them in ~Factory.zipWith~. Membership proofs and user
constructors still need to follow their capability types. This is a maintenance
contract, not a measured resolver throughput improvement.

* Adapt existing proposition-valued theorems

~Factory.fromProof prove~ accepts ~prove : ∀ context, Claim context~ for
~Claim : Context → Prop~ and returns ~Factory Context (fun c => PLift (Claim c))~.
Its result's ~down~ is a proof of the exact supplied context's claim;
~fromProof_down~ is definitionally equal to the existing theorem call and
requires no axioms. This bridges the result sort without rewriting analytic
proofs. Context/guard binding and noncomputable source behavior remain caller
responsibilities.

* Declare only the capabilities a consumer uses

Import ~LeanPoo.Functional.View~. Give the consumer a type
~Requirements.Factories Context Value needs → Result~ where ~needs~ lists its
actual dependencies. Keep source-list positions, provider registry, and graph
outside that function. For independent consumers, call ~prepare provider needs~
directly: a missing unrelated capability must not become a global startup gate.

When a larger family has already been prepared, call
~Requirements.project retained needs included~, with
~included : ∀ key ∈ needs, key ∈ source~. The result has the consumer's exact
list and dependent result types. Projection can reorder or repeat keys and
runs no factory or provider lookup. It scans the source once per requested key;
retain the projected tuple before repeated context calls. It neither generates
adapters nor removes source capabilities.

~project_selected~ preserves the selected-function contract, so original C4
provenance remains available through ~factoryAt_origin~ and ~project_ready~.
~project_ready~ proves agreement with independent local preparation.
~project_stable~ compares different successful source lists and different
providers, requiring function equality only for ~needs~. The two lists may
contain different unrelated capabilities. ~consumer_stable~ transfers exact
results of any function using this narrow interface. Results can themselves be
functions over all contexts; equality also transports an existing proposition
about the result, as compiled in [[file:../Tests/FunctionalView.lean][FunctionalView]].

The contract fixes ~Context~, ~Key~, and ~Value~. Changed requested functions,
changed proposition statements, and changed context/result types require new
compatibility evidence. Equality of functions is sufficient and can be proved
extensionally; observational similarity alone does not discharge that premise.
This prevents unrelated source edits from requiring consumer-expression or
consumer-theorem changes under the stated conditions. It does not stop Lean
from recompiling modules whose imports changed, nor establish an elapsed-time
improvement.

* Preserve an observation interface across representation changes

Import ~LeanPoo.Functional.Observation~ when implementations expose different
representation types but share a public semantic interface. Declare
~Observed : Context → Key → Type~, with two maps
~expose : ∀ c k, Value c k → Observed c k~ and
~reveal : ∀ c k, Other c k → Observed c k~. Give consumers only the observed
factories. Values, representations, and contexts remain explicitly indexed;
the library does not select a suitable observation for the application.

~Requirements.Related relation keys left right~ records pointwise compatibility
of retained functions, allowing different original result families.
~RelatedOn provider other needs relation~ declares this condition only for
selected pairs of factories on ~needs~. It does not imply availability or
missing-key error equivalence. ~project_related~ derives related narrow views
from two successful preparations, with only the declared keys in its premise.
It also handles distinct source lists and repeated consumer keys.

~Requirements.observe expose retained~ constructs the public factories without
invoking the original factories or the observation map. Invocation later runs
the original function and its map. Observation can have a cost; retain these
public factories before repeated use. No observation is memoized or assumed
constant-time. If the two maps yield equal observations at every supplied
context, ~observe_congr~ proves the public factory tuples equal and
~observed_consumer_stable~ preserves any consumer result. This includes results
that are themselves context functions and transfers propositions about them.
The [[file:../Tests/FunctionalObservation.lean][compiled test]] exercises distinct representations, dependent guards, a deleted
unrequested capability, reordered source lists, and repeated consumer keys.

Only exposed observations are preserved. A claim about hidden metadata cannot
be transferred from equality of paths alone. If a consumer needs a bound or
proof witness, expose the relevant property or prove its relationship to the
observation explicitly. The test rejects a changed public value and use of a
witness from a different context. Context/key/public observation type changes
still need explicit typed adapters. Original C4 selections need not be equal;
the selected implementations must satisfy the stated pointwise relation.

The Euler reference already contains a path-to-field-tower bridge. Reusing it
as compatibility evidence would be application-owned; no external adapter or
large-library migration has been compiled here. See the [[file:use-cases/euler-maintenance-checklist.org][research checklist]].

* Retarget existing evidence to equal replacement data

Import ~LeanPoo.Functional.Transport~. After establishing equality of the data
produced by two implementations, ~Factory.transport~ reuses an existing witness
family and gives it the exact replacement index:

#+begin_src lean
example {Context : Type} {Data : Context → Type}
    (Certificate : (c : Context) → Data c → Type)
    (old new : Functional.Factory Context Data)
    (same : ∀ c, old c = new c)
    (existing : Functional.Factory Context (fun c => Certificate c (old c))) :
    Functional.Factory Context (fun c => Certificate c (new c)) :=
  Functional.Factory.transport Certificate same existing
#+end_src

The witness may be a record containing data, proof fields, and further
quantified obligations. Its implementation is retained. ~transport_refl~
preserves identity, ~transport_trans~ equates chained and direct migration,
and ~transport_roundtrip~ restores the exact original witness family after
migration back. These laws apply to arbitrary dependent witnesses.

For an existing theorem ~prove : ∀ c, Claim c (old c)~, call
~Factory.transportProof Claim same prove~ to obtain ~∀ c, Claim c (new c)~.
It returns Prop directly and requires no axioms. If a Type-valued proof factory
is required by a provider, wrap the result with ~Factory.fromProof~. No analytic
proof is synthesized: the old theorem and the data equality remain prerequisites.

The observation pipeline supplies that equality. If a consumer returns a data
factory, ~observed_consumer_stable~ gives equality of the old and replacement
data factories. Use ~fun c => congrFun dataEqual c~ as the transport premise.
The [[file:../Tests/FunctionalTransport.lean][generic compiled client]] connects these APIs without assuming identical
original representation types. This factors the common migration step out of
individual analytic consumers.

Transport fixes the context and the entire datum indexed by the witness.
Equality of one projected field cannot retarget evidence indexed by a larger
unequal record. Changed context types, changed claims, or merely ordered/
approximately equal data require an explicit application-specific adapter or
proof. The retained witness body keeps its original computation; this API does
not remove legacy computations or establish a runtime improvement. The
[[file:use-cases/euler-maintenance-checklist.org][reference research checklist]] records an existing Euler data-equality rewrite
with the same dependent-index shape, without claiming an external migration.

* Reuse a capability family in an extended context

Import ~LeanPoo.Functional.Reindex~. Supply one explicit

and ~assemble_reindex~ preserve first-provider selection and reuse the same
verified C4 order. No new graph compilation is required.

Alternatively retain a successful checklist once and call

* Reuse verified orders after registry declaration reordering

Import ~LeanPoo.C4.Presentation~ and ~LeanPoo.Functional.Presentation~.
Keep each node's exact name, local parent rows and suffix flag. Supply
~same : graph.nodes.Perm other.nodes~ and
~unique : (graph.nodes.map C4.Node.name).Nodup~. The permutation concerns the

~VerifiedOrder.permute~ retains the existing output list without mapping it or

become accepted under these premises. It does not equate error payloads:
validation reports its first invalid reference in declaration-list order.

~Requirements.prepare_permute~ preserves exact functions and first missing

No factory is invoked by retained-order migration.

does not infer equivalence of edited declarations. Duplicate names can change
first lookup when reordered and are outside this guarantee. The more general

Provider alignment is essential: the [[file:../Tests/C4Relabeling.lean][compiled client]] shows an entry becomes

own mapping construction, provider adapters, injectivity, exact declaration

prove arbitrary finite graph-isomorphism extension, changed local parent orders,

* Build the migrated provider registry automatically

Import ~LeanPoo.Functional.Registry~. Use one retained hash registry rather than
writing an inverse name map, one branch per provider and an alignment lemma:

#+begin_src lean

    {graph other : C4.Graph} (order : C4.VerifiedOrder graph root)
    (change : graph.Relabeling other)
    (unique : (graph.nodes.map C4.Node.name).Nodup)

In executable client code, retain ~registry := ProviderRegistry.relabel order
change providers~ once, then give ~registry.dictionary~ to ~assemble~ with the

stored provider through a hash query. No capability enumeration, ~DecidableEq

cannot serve an unrelated root without rebuilding an appropriate ancestor cut.
Source graph uniqueness and the explicit relabeling witness remain prerequisites
for migrated verified orders; the registry does not infer graph equivalence.

Construction traverses the retained ancestor list once and stores one whole
provider function per mapped name. It computes the name map and obtains each
provider function, so application dictionary construction can have a cost.
Later dictionary access hashes/compares names; worst-case collision behavior and
string costs remain. Retaining prepared factories avoids repeated registry
queries. This is a reusable hash index, not an elapsed-time speedup claim or
factory-result cache. Original contexts, proof guards, keys, data payloads and
factory bodies remain exact; embedded payload names are not rewritten.

Import ~LeanPoo.Functional.SharedRegistry~. A multi-root application can retain
~registry := ProviderRegistry.ofGraph graph providers~ once, then use
~assemble left registry.dictionary~ and ~assemble right registry.dictionary~
with independently verified orders of that same graph. Prepare each consumer's
key list once and retain its factories. No per-root provider table, key
enumeration, inverse name map or alignment proof is required. The constructor
obtains provider functions but does not invoke factories or compile roots.

The generic preservation contract is:

#+begin_src lean

    {graph : C4.Graph} (order : C4.VerifiedOrder graph root)

~ofGraph_lookup~ preserves every declared provider; ~ofGraph_missing~ excludes
undeclared application names. ~assemble_ofGraph_registry~ and
~prepare_ofGraph_registry~ work for any verified root of the graph, without a
new global name-uniqueness or migration premise. The index does not validate a
graph: the assembly contracts still require a ~VerifiedOrder~.

For an explicit migration, retain ~ProviderRegistry.relabelGraph change
providers~ once and share its dictionary across all migrated orders.

The scope choice is observable. A declared unrelated provider is present in a
shared dictionary, while it is absent from a root-cut dictionary. ~assemble~
still searches only that root's verified ancestor order, so an unrelated entry

Undeclared providers are absent from either shared constructor. Compiled

of the retained ancestor-list lengths. Sharing reduces those construction

many unused declarations can make it more expensive. The local two-root
fixture has five declarations versus six summed ancestor entries, a structural
count only. Hash/string costs, factory invocation and result data remain. No
runtime speedup or actual Euler maintenance saving is inferred from these counts.

* Patch one capability and reuse unaffected consumers

Import ~LeanPoo.Functional.RegistryPatch~. This API requires ~DecidableEq Key~
for typed single-key updates and checklist membership. Retain each root's
~order.indexAncestors~ once. Apply ~registry.patch name key replacement~, where
~replacement~ is ~some factory~ to add/replace a capability or ~none~ to remove
it. Unknown provider names return ~.error name~; a successful patch retains
exactly the old provider-name scope and leaves the original registry usable.
The graph and verified orders are unchanged. The supplied factory must still
inhabit the original context-indexed result contract.

For each consumer, query ~Requirements.mayAffect index keys name key~. This
combines indexed ancestry with membership in that consumer's explicit key list.
When false, keep its old prepared factories and use
~Requirements.prepare_patch_of_unaffected~ to retain their selection proof and
arbitrary consumer-result claims. There is no provider-alignment premise,
capability-by-capability ~require~ rewrite or analytic equivalence obligation
for the unaffected consumer. The compiled [[file:../Tests/FunctionalRegistryPatch.lean][generic client]] is:

#+begin_src lean
example {Context Key : Type} [DecidableEq Key] {Value : Context → Key → Type}
    {graph : C4.Graph} (index : C4.AncestryIndex graph root)
    (registry updated : Functional.ProviderRegistry Context Key Value)
    (name : String) (key : Key)
    (replacement : Option (Functional.Factory Context (fun c => Value c key)))
    (keys : List Key) (applied : registry.patch name key replacement = .ok updated)
    (unaffected : Functional.Requirements.mayAffect index keys name key = false) :
    Functional.Requirements.prepare (Functional.assemble index.order updated.dictionary) keys =
      Functional.Requirements.prepare (Functional.assemble index.order registry.dictionary) keys :=
  Functional.Requirements.prepare_patch_of_unaffected index registry name key replacement keys applied unaffected

~patch_at~ establishes the edited cell, ~patch_other~ preserves exact functions
at other names/keys, and ~patch_scope~ preserves provider-name membership.
~prepare_patch_stable~ also accepts the explicit negative ancestry or key-list
premise without executing an impact query. First missing capabilities and
successful tuples are both preserved by the negative contract, for all contexts.

A true impact query is a candidate for rechecking, not proof of a changed result.
A more specific provider may shadow the edited provider; preparation may also
stop at an earlier missing key. The corpus includes an explicit A-before-B
shadow case with true candidate impact and unchanged selected quantity. Actual
change, observation equivalence and broader proof dependency closure require
additional evidence. Changes to graph orders or context/key/result families
are outside this contract.

One patch performs a name lookup and a persistent hash insertion; it does not
fold graph declarations, reconstruct orders or acquire all other provider
functions. Retaining old snapshots can cause underlying hash storage copies.
Capability lookup adds key-equality checks; repeated edits can accumulate
provider-wrapper chains, which this API does not compact. An impact query adds
an ancestry hash lookup and a linear checklist membership check. No constant-
time, end-to-end speedup or factory-result cache is claimed. Preparing factories
once avoids repeated dictionary/key selection during context application.

* Normalize edits and restore saved capabilities

The same RegistryPatch import supplies ~Provider.patchKey_overwrite~: two
edits of the same key equal just the final edit of the original provider.
~patchKey_commute~ allows distinct keys to be reordered, retaining their
individual dependent result families. ~patchKey_restore~ proves that writing
the original cell back is an identity. These are function equalities across
all contexts, including absent capabilities. Use them to prove an explicitly
normalized edit plan. They do not compact a closure already constructed at
runtime, nor define a general batch optimizer.

For rollback, retain the original cell ~registry.dictionary name key~ (or the
original registry), then call ~edited.patch name key savedCell~. A successful
initial edit guarantees the rollback name still exists, by
~ProviderRegistry.patch_restore_exists~. ~patch_restore~ proves exact dictionary
equality with the original, without asserting physical hash-table identity.
~Requirements.prepare_patch_restore~ restores any root's whole checklist,
including first errors. A generic compiled client in FunctionalRegistryPatch
transports an arbitrary old consumer claim by one rewrite; no impact query,
per-key requirement rewrite, or new factory invocation is needed for its proof.

The rollback must immediately undo that one edit, or the client must separately
prove that intervening edits are preserved. Restoring one cell is not a rollback
of arbitrary concurrent changes. Construction performs another persistent hash
lookup/insertion and adds another key-check wrapper; retain original prepared
factories or normalize from the saved original provider to avoid that chain.
No constant-time or measured performance improvement is asserted.

* Compile capability edits into a normalized overlay

Import ~LeanPoo.Functional.Overlay~. ~CapabilityEdit Context Key Value~ is a
heterogeneous pair: a capability key and an optional factory in that exact
key's dependent result family. ~none~ explicitly removes the capability; an
absent override delegates to the original provider. ~DecidableEq Key~ suffices;
no key hashing, global finite-key enumeration or factory evaluation is required.

Start ~ProviderOverlay.ofProvider original~ once. Retain that overlay and update
it through ~overlay.set key replacement~. Each set removes the previous entry
of that key and prepends its new entry. The structure retains a proof that
stored keys are unique. Alternatively use one ~ProviderOverlay.compile original
edits~ call on a caller-ordered edit list. Later edits of the same key win.
~overlay.provider~ supplies the ordinary Provider interface for ~Requirements~,
~assemble~, or a provider dictionary passed to ~ProviderRegistry.ofGraph~.

~set_provider~ proves exact equality with one old ~patchKey~ operation;
~compile_provider~ proves exact equality with sequential patching of the entire
batch, across all contexts and arbitrary dependent value families.
~Requirements.prepare_overlay_compile~ transports whole-checklist results,
including their first missing keys. The compiled generic test client reuses an
arbitrary old consumer claim by one rewrite, with no per-key ~require~ or
per-step provider-alignment proof. A minimal typed usage is:

#+begin_src lean
def edited {Context Key : Type} [DecidableEq Key] {Value : Context → Key → Type}
    (original : Functional.Provider Context Key Value)
    (edits : List (Functional.CapabilityEdit Context Key Value))
    (keys : List Key) :=
  Functional.Requirements.prepare (Functional.ProviderOverlay.compile original edits).provider keys
#+end_src

Retain the compiled overlay or prepared factories; repeatedly rebuilding the
batch would repeat normalization. Queries linearly scan distinct stored override
keys, then call the base only if none matches. They do not traverse the history
of overlay sets. In contrast, sequential ~patchKey~ stores a closure per edit.
Compilation of h edits over d distinct keys scans up to the current d overrides
per set and allocates filtered lists; this can cost quadratic work when every
key is new. It is not a hash-indexed lookup or a constant-time API. The base may
already contain wrapper chains; wrapping such a base does not compact them.
Keep the original base when compiling a long edit history. Explicit ~none~ is
retained as an override and must not be discarded as a missing edit.

The local fixture checks 32 histories and 344 prefix updates against an
independent last-cell oracle, including 5504 prefix and 512 final batch
checklist observations at two contexts. A 256-edit same-key history stores one
override; this is a structural reduction in stored edits and potential key
checks, not a runtime speedup or Euler source saving. No arbitrary transaction,
provider-name migration or analytic dependency equivalence is inferred.

* Apply a normalized capability batch directly to a shared registry

Import ~LeanPoo.Functional.RegistryBatch~. Call ~registry.patchBatch name edits~
with the same typed ~CapabilityEdit~ list used by ProviderOverlay. The API
checks the provider name once, compiles a normalized overlay over its retained
original provider, and installs it with one insertion. No handwritten dictionary
branch, provider-alignment proof, graph declaration fold or factory invocation
is needed. Unknown names return that exact name as error, including an empty
batch. Known-name empty batches retain all original dictionary functions.

A successful batch preserves provider-name membership, every other provider's
entire function, and every unedited key even at the target provider. Later
same-key edits win; explicit removal stays distinct from base fallback.
~patchBatch_dictionary~ supplies whole-dictionary equality to the sequential
single-provider reference. This is equality of selected functions at all
contexts, not physical hash-table identity or a new mathematical equivalence
between unrelated factories.

Retain each root's ancestry index once. Query
~Requirements.batchMayAffect index keys name edits~ for each consumer. False
means either the provider is outside that root or its requested key list is
disjoint from the batch footprint. Use ~prepare_patchBatch_of_unaffected~ to
reuse exact prepared tuples, first errors and arbitrary consumer claims by one
rewrite. The generic compiled client in FunctionalRegistryBatch requires no
per-key ~require~ or untouched-provider alignment proofs. The explicit
~prepare_patchBatch_stable~ theorem also accepts the negative scope premise.
A true query is conservative: earlier providers or missing keys may hide edits.

Normalization covers the supplied batch. Applying another batch over an already

* Choosing representation with native and retained-state evidence

not change graph/type/dependency premises or infer Euler proof equivalence.

* Atomic transactions on retained indexed registries

Import ~LeanPoo.Functional.IndexedTransaction~. Use the same ~RegistryEdit~ list
and ~Requirements.transactionMayAffect~ predicate as ordinary registry clients.
Call ~state.patchTransaction changes~ once and publish only its ~.ok updated~
result. An empty transaction returns the original state. Repeated names execute
in caller order; an unknown name, even with an empty batch, stops with that name.
A successful prefix is never returned on failure. The original immutable state
and prepared views remain available; this is pure return-value atomicity.

Unlike chaining individual batches in caller code, this API packages sequencing
and first-error handling. ~patchTransaction_base~ proves that every original base
is retained. ~patchTransaction_scope~ preserves the complete name membership.
Each reached successful batch does one name lookup/insertion and indexed writes.
There is no full-table snapshot, graph rebuild or factory invocation in the path.
Hash collisions, persistent copies and retaining old versions remain costs.

For a successful transaction with negative ancestor/key read scope, reuse an
arbitrary consumer claim with one rewrite:

#+begin_src lean
example {Context : Type u} {Key : Type v}
    [BEq Key] [Hashable Key] [LawfulBEq Key] [DecidableEq Key]
    {Value : Context → Key → Type w} {Result : Type x}
    (index : C4.AncestryIndex graph root)
    (state updated : Functional.IndexedRegistry Context Key Value)
    (changes : List (Functional.RegistryEdit Context Key Value)) (keys : List Key)
    (applied : state.patchTransaction changes = .ok updated)
    (unaffected : Functional.Requirements.transactionMayAffect index keys changes = false)
    (consume : Functional.Requirements.Factories Context Value keys → Result)
    (Claim : Except Key Result → Prop)
    (known : Claim ((Functional.Requirements.prepare
      (Functional.assemble index.order state.dictionary) keys).map consume)) :
    Claim ((Functional.Requirements.prepare
      (Functional.assemble index.order updated.dictionary) keys).map consume) := by
  rw [Functional.Requirements.prepare_indexedTransaction_of_unaffected
    index state changes keys applied unaffected]
  exact known
#+end_src

This covers all contexts, repeated consumer keys and first missing-key errors.
It removes caller per-batch proof chaining and per-key ~require~ scaffolding for
unaffected consumers. A positive candidate still needs explicit alignment;
negative scope does not suppress unknown-name errors. The reference Euler tower
could group named analytic-provider changes before reusing an unaffected
consumer, once a user supplies typed providers and actual dependency scopes.
No such external adapter or consumer migration is implemented here.

* Transfer complete transaction consumers between representations

Import ~LeanPoo.Functional.IndexedTransaction~. Once a client has a scoped
~ProviderRegistry~, convert it with ~IndexedRegistry.ofRegistry~ and pass the same
~RegistryEdit~ transaction. ~ofRegistry_patchTransaction~ proves equality of the
complete ~Except String~ dictionary result: all successful provider functions
and the first unknown-name error agree. A success premise and negative impact
check are unnecessary for this representation comparison.

~ofRegistry_transaction_consumer~ transfers any dictionary consumer, including
C4 assembly, heterogeneous preparation, caller-context evaluation and arbitrary
claims about the resulting nested errors. For example:

#+begin_src lean
example {Context : Type u} {Key : Type v}
    [BEq Key] [Hashable Key] [LawfulBEq Key] [DecidableEq Key]
    {Value : Context → Key → Type w} {Result : Type x}
    (index : C4.AncestryIndex graph root)
    (registry : Functional.ProviderRegistry Context Key Value)
    (changes : List (Functional.RegistryEdit Context Key Value)) (keys : List Key)
    (consume : Functional.Requirements.Factories Context Value keys → Result)

    (known : Claim ((registry.patchTransaction changes).map (fun updated =>
      (Functional.Requirements.prepare
        (Functional.assemble index.order updated.dictionary) keys).map consume))) :
    Claim (((Functional.IndexedRegistry.ofRegistry registry).patchTransaction changes).map
      (fun updated => (Functional.Requirements.prepare
        (Functional.assemble index.order updated.dictionary) keys).map consume)) := by
  rw [Functional.IndexedRegistry.ofRegistry_transaction_consumer registry changes
    (fun dictionary => (Functional.Requirements.prepare
      (Functional.assemble index.order dictionary) keys).map consume)]
  exact known

For already aligned custom states, ~patchTransaction_congr~ takes exact dictionary
agreement plus equal name membership. Both conditions matter: a registered empty
provider has the same dictionary functions as an unknown name, but an empty batch
at that name succeeds in only the registered case. The tests prove this full
function equality and execute the distinct outcomes.

This supports changing storage representation while keeping existing transaction
consumer proofs, including affected keys. It compares the same transaction on
two representations. To reuse a claim across different old/new changes, use the
negative-scope theorem or provide explicit alignment for affected consumers.
No new runtime algorithm or performance threshold is introduced by these proofs.

* Optional name-only transaction preflight

Import ~LeanPoo.Functional.TransactionCheck~. Both ordinary and indexed registries
expose ~registry.checkTransaction changes : Except String Unit~. It stops at the
first unknown name in caller order, including names paired with empty batches.
It queries only initial name membership: no capability-edit cells, factories,
update tables, graph resolution or explicit snapshots are needed during the check.
Inputs still have their own construction cost.

Use this for a dry-run diagnostic or before allocating a large successful prefix
that might later be rejected. On ~.ok ()~, the caller can execute the transaction
and then prepare its consumer. ~checkTransaction_outcome~ proves that the check
has exactly the actual transaction's success/first-name-error result. It does not
promise requested capabilities: a registered empty provider passes preflight but
its preparation can still return a missing key. Factory guards remain typed and
caller-owned.

Successful transactions preserve membership, so cache a name-check result across
updates with one rewrite instead of checking/alignment proofs for each name:

#+begin_src lean
example {Context : Type u} {Key : Type v} [BEq Key] [Hashable Key]
    {Value : Context → Key → Type w}
    (registry updated : Functional.IndexedRegistry Context Key Value)
    (changes pending : List (Functional.RegistryEdit Context Key Value))
    (applied : registry.patchTransaction changes = .ok updated)
    (Claim : Except String Unit → Prop)
    (known : Claim (registry.checkTransaction pending)) :
    Claim (updated.checkTransaction pending) := by
  rw [Functional.IndexedRegistry.checkTransaction_after registry updated changes pending applied]
  exact known
#+end_src

~ofRegistry_checkTransaction~ preserves the check during storage conversion;
~checkTransactionNames_congr~ covers explicitly equal name scopes. A different
name scope needs new validation. ~checkTransactionNames_ok_iff~ characterizes
success as every batch name being registered, regardless of repeated names/keys.

Each reached batch needs one name membership query, stopping at the first absent
name. Hash/collision costs remain. Preflight followed by a successful transaction
adds another name scan; this is optional and does not replace normal execution.
No elapsed-time or allocation improvement has been measured. This API packages
name diagnostics and their exact reuse contracts; it does not infer analytic
provider dependencies or migrate an external Euler consumer.

* Prepare a consumer transaction view with a conservative fast path

Import ~LeanPoo.Functional.ScopedTransaction~. Call
~Requirements.prepareTransaction index registry changes keys~ to obtain
~Except String (Except Key (Factories Context Value keys))~. It returns a
consumer view; it does not return an updated registry for publication.

A negative ~transactionMayAffect~ checks all transaction names, then prepares
from the original dictionary without constructing update prefixes or writing
capability cells. Thus out-of-scope unknown names are still errors, including
empty batches. A positive candidate runs the full transaction and prepares its
result. Missing capabilities, repeated keys, caller order and all future context
applications preserve exactly the full path's semantics. No factory executes
during preparation. This is conservative: shadowed edits can take the positive
path, and disjoint keys still need edit-cell scans.

~prepareTransaction_eq~ rewrites to the full indexed transaction for arbitrary
clients. ~prepareTransaction_ofRegistry~ transfers an ordinary client directly:

#+begin_src lean
example {Context : Type u} {Key : Type v}
    [BEq Key] [Hashable Key] [LawfulBEq Key] [DecidableEq Key]
    {Value : Context → Key → Type w} {Result : Type x}
    (index : C4.AncestryIndex graph root)
    (registry : Functional.ProviderRegistry Context Key Value)
    (changes : List (Functional.RegistryEdit Context Key Value)) (keys : List Key)
    (consume : Functional.Requirements.Factories Context Value keys → Result)
    (Claim : Except String (Except Key Result) → Prop)
    (known : Claim ((registry.patchTransaction changes).map (fun updated =>
      (Functional.Requirements.prepare
        (Functional.assemble index.order updated.dictionary) keys).map consume))) :
    Claim ((Functional.Requirements.prepareTransaction index
      (Functional.IndexedRegistry.ofRegistry registry) changes keys).map
        (fun ready => ready.map consume)) := by
  rw [Functional.Requirements.prepareTransaction_ofRegistry]
  cases applied : registry.patchTransaction changes <;>
    simpa only [applied, Except.map] using known
#+end_src

The API packages update/preflight/prepare branching and its proof, reducing caller
per-key ~require~ and branch-alignment scaffolding. It does not infer the user's
analytic dependencies. Use full ~patchTransaction~ when publishing updated state;
sharing one already-updated registry can amortize work across many consumers.

The paired native receipt measures the whole call, including impact checks.
Outside-name medians are 0.124/0.011 ms full/scoped; disjoint-key medians are
0.187/0.145 ms; late unknown-name medians are 0.119/0.009 ms. Positive fallback
is slightly slower, 0.118313/0.119542 ms. Graph/index/registration/conversion,
inputs, factory execution and scalar validation are outside timers. Four local
alternating pairs per workload establish no universal crossover, allocation
saving or whole Euler speedup.

* Retain a requested-key index across transaction views

Import ~LeanPoo.Functional.KeyIndex~. Build
~let scope := Requirements.KeyIndex.ofKeys keys~ once, then use
~Requirements.prepareTransactionIndexed ancestry scope registry changes~ for
repeated plans. The ancestry index is already retained; this adds a verified hash
index for requested-key membership. It removes repeated requested-list scans
inside the edit-history loop. Raw edit histories still scan until first overlap.

~KeyIndex keys~ ties membership to the exact list. The set deduplicates only
impact queries: preparation retains original order, repeated keys, dependent
result types, first capability errors and all future context functions.
~transactionMayAffectIndexed_eq~ and ~prepareTransactionIndexed_eq~ prove exact
agreement with the existing list path. Collisions are permitted; correctness
does not depend on average hash performance. Rebuild for a different requested
list; an index can be shared across roots/registries with the same list.

#+begin_src lean
example {Context : Type u} {Key : Type v}
    [BEq Key] [Hashable Key] [LawfulBEq Key] [DecidableEq Key]
    {Value : Context → Key → Type w} {Result : Type x}
    (ancestry : C4.AncestryIndex graph root)
    (keys : List Key)
    (scope : Functional.Requirements.KeyIndex keys)
    (registry : Functional.ProviderRegistry Context Key Value)
    (changes : List (Functional.RegistryEdit Context Key Value))
    (consume : Functional.Requirements.Factories Context Value keys → Result)
    (Claim : Except String (Except Key Result) → Prop)
    (known : Claim ((registry.patchTransaction changes).map (fun updated =>
      (Functional.Requirements.prepare
        (Functional.assemble ancestry.order updated.dictionary) keys).map consume))) :
    Claim ((Functional.Requirements.prepareTransactionIndexed ancestry scope
      (Functional.IndexedRegistry.ofRegistry registry) changes).map
        (fun ready => ready.map consume)) := by
  rw [Functional.Requirements.prepareTransactionIndexed_ofRegistry]
  cases applied : registry.patchTransaction changes <;>
    simpa only [applied, Except.map] using known
#+end_src

This combines retained ancestry/key scope, exact name diagnostics and typed
consumer preparation without user branch/per-key ~require~ proofs. It remains a
consumer view, not updated state publication. Full ~patchTransaction~ still
publishes changes. Hash collisions, copies, set construction, scope scans,
preparation and user factory costs remain.

Native evidence separates index construction from retained use. For 512 requested
keys and 4,096 disjoint edits, list/indexed query medians are 21.014521/0.063708 ms;
indexed per-sample build+query median is 0.084354 ms. Late overlap gives
20.979250/0.156208 ms, with indexed total 0.175458 ms. For 512-key outside
ancestry, totals regress from 0.048500 to 0.071521 ms; early overlap from
0.152521 to 0.174750 ms; unknown names from 0.005730 to 0.025313 ms. Eight-key
outside/unknown one-use totals also regress. Retain/choose the index by workload;
there is no automatic global crossover. These local calls exclude factory bodies
and graph/ancestry/registration/conversion/inputs/build/oracle costs, and do not
measure allocated bytes, peak memory or Euler maintenance savings.

* Prepare and retain a joint consumer certificate

Import ~LeanPoo.Functional.CertifiedRequirements~. ~Requirements.Certified keys
Claim~ retains the complete heterogeneous factory tuple and an explicit proof
~∀ context, Claim context (Requirements.build factories context)~. The claim can
relate several selected capabilities: a pressure value and its gradient/equation
guards, or a quantity, limit and enabled flag. This is an additional Lean client
contract layer; POOF's record/prototype model does not supply analytic proofs.

#+begin_src lean
example {Context : Type u} {Key : Type v}
    {Value : Context → Key → Type w} (keys : List Key)
    (provider : Functional.Provider Context Key Value)
    (Claim : ∀ c, Functional.Requirements.Results Value c keys → Prop)
    (admit : ∀ factories,
      Functional.Requirements.Selected provider keys factories →
      ∀ c, Claim c (Functional.Requirements.build factories c)) :
    (Functional.Requirements.prepareCertified provider keys Claim admit).map
      Functional.Requirements.Certified.factories =
      Functional.Requirements.prepare provider keys :=
  Functional.Requirements.prepareCertified_forget provider keys Claim admit
#+end_src

- ~prepareCertified provider keys Claim admit~ selects once and returns either
  the original first missing key or the complete functions with their joint proof.
  The admission premise must hold for the exact provider-selected tuple. It is
  vacuous when no full tuple can be selected, so missing-key clients need no fake
  successful certificate.
- ~ready.build context~ returns ~{data // Claim context data}~. Read ~.val~ for the
  results and ~.property~ for the proof, avoiding repeated per-key ~require~ calls.
- ~certify factories Claim valid~ attaches an existing joint proof to a tuple from
  any preparation path, including indexed/scoped transactions. It adds no second
  provider lookup or branch selection.
- ~prepareCertified_congr~ transfers exact certified outcomes from equal complete
  preparation results, even with different admission proof terms. Use
  ~prepare_congr~ to discharge its premise when providers agree on requested keys.
  ~prepareCertified_error_iff~ retains the exact first error.

~Claim~ lives in ~Prop~ and is erased at runtime. Data/functions still have their
normal cost; factory bodies execute on every build. There is no runtime predicate
checker, automatic dependency analysis, or analytic proof synthesis. Put
Type-valued pressure/evidence data in the result family; ~Factory.transport~
remains available for data-indexed Type witnesses. A changed context, key family,
or joint predicate requires aligned data/proofs. A local negative type check
rejects using results prepared at context 0 as context 9.

Shared API/proofs: 104 physical lines; semantic/client fixture: 115 lines. These
are added local costs, not Euler source savings. Local validation covers 192
availability/order/duplicate/empty preparations plus 8 joint-contract plans at
three future contexts; six kernel axiom reports. No runtime speedup is measured.

* Reuse the prepared tuple and joint proof across irrelevant transactions

Import ~LeanPoo.Functional.CachedPreparation~. Prepare
~cacheCertified provider keys Claim admit~ once and retain a ~KeyIndex keys~.
~CachedPreparation provider keys Claim~ binds both cached success and first-key
failure to the exact original provider. ~prepareTransactionCached~ returns:

- A transaction name error, including unknown empty batches.
- ~TransactionPreparation.reused cached~ after a negative ancestry/key scope
  check and successful name preflight. This is the original complete outcome;
  successful cached functions retain their supplied joint proof at all contexts.
- ~TransactionPreparation.fresh prepared~ after conservative positive impact.
  This contains complete freshly prepared data/errors, without the old joint
  proof. Attach a new proof with ~certify~ after a successful fresh result. A
  positive scope only says revalidation is needed, not that the old claim is false.

#+begin_src lean
example {Context : Type u} {Key : Type v}
    [BEq Key] [Hashable Key] [LawfulBEq Key] [DecidableEq Key]
    {Value : Context → Key → Type w} (keys : List Key)
    (Claim : ∀ c, Functional.Requirements.Results Value c keys → Prop)
    (index : C4.AncestryIndex graph root)
    (registry : Functional.IndexedRegistry Context Key Value)
    (edits : List (Functional.RegistryEdit Context Key Value))
    (cache : Functional.Requirements.CachedPreparation
      (Functional.assemble index.order registry.dictionary) keys Claim) :
    (Functional.Requirements.prepareTransactionCached index
      (Functional.Requirements.KeyIndex.ofKeys keys) registry edits cache).map
        Functional.Requirements.TransactionPreparation.forget =
    (registry.patchTransaction edits).map (fun updated =>
      Functional.Requirements.prepare
        (Functional.assemble index.order updated.dictionary) keys) :=
  Functional.Requirements.prepareTransactionCached_forget index
    (Functional.Requirements.KeyIndex.ofKeys keys) registry edits cache
#+end_src

~prepareTransactionCached_forget~ proves exact full transaction semantics after
forgetting the reuse tag/certificate. ~prepareTransactionCached_ofRegistry~
transfers that contract from ordinary storage. ~prepareTransactionCached_unaffected~
returns the exact retained outcome, while ~prepareTransactionCached_affected~
exposes the full update path and fresh proof obligation. The negative path adds
no capability lookup, preparation, update table or factory execution; raw impact
cells and name preflight still scan. The retained tuples/indexes cost memory.

The API gives a view relative to its explicit registry/graph/root/key list; it
does not publish updated state or automatically rebind a cache for later registry
revisions. Use full ~patchTransaction~ for state publication and provide exact
alignment when rebinding a cache. Fixed closed factories are not a dependency
tracker for open-recursive objects or arbitrary analytic callbacks. Changed
contexts/result families and provider views require new alignment; the fixture
rejects silently supplying a cache for another provider.

Added shared code/proofs: 101 physical lines; semantic fixture: 175; native Lean/
Python study: 56/65. Tests cover 4096 plans, 2304 negative and 1792 positive scopes,
1024 first-name errors, collisions, cached missing-key failures and two contexts;
four standard-only axiom reports. These are local costs, not measured Euler savings.

* Publish a full transaction and continue with an aligned consumer cache

Import ~LeanPoo.Functional.ConsumerRevision~. ~applyTransactionCached~ always
applies the full immutable transaction, preserving edits outside this consumer.
It returns the first unknown name with no updated prefix, or a ~ConsumerRevision~:

- ~.reused updated cache~ publishes ~updated~ and carries the old complete
  certified outcome with alignment to that new registry supplied by the library.
  This cache can go directly into the next transaction with the same graph/root,
  key list, context/result family and joint claim. No per-name/key alignment proof
  or fresh joint proof is required in this branch.
- ~.fresh updated prepared~ publishes ~updated~ and carries exact new data/errors
  in ~Prepared~. ~prepared.certify Claim admit~ attaches the supplied new analytic
  proof to the saved tuple without preparing again. The resulting cache is tied
  to ~updated~ and can continue the next transaction.

~ConsumerRevision.registry~ and ~forget~ expose the complete state and ordinary
consumer outcome. ~ConsumerRevision.certify~ is a convenience when an admission
proof for the returned provider is available; it returns reused caches directly.
Branch explicitly on ~.reused~ when no fresh admission is needed. Merely receiving
fresh data does not supply an analytic proof.

#+begin_src lean
example {Context : Type u} {Key : Type v}
    [BEq Key] [Hashable Key] [LawfulBEq Key] [DecidableEq Key]
    {Value : Context → Key → Type w} (keys : List Key)
    (Claim : ∀ c, Functional.Requirements.Results Value c keys → Prop)
    (index : C4.AncestryIndex graph root)
    (registry : Functional.IndexedRegistry Context Key Value)
    (edits : List (Functional.RegistryEdit Context Key Value))
    (cache : Functional.Requirements.CachedPreparation
      (Functional.assemble index.order registry.dictionary) keys Claim) :
    (Functional.Requirements.applyTransactionCached index
      (Functional.Requirements.KeyIndex.ofKeys keys) registry edits cache).map
        Functional.Requirements.ConsumerRevision.registry =
      registry.patchTransaction edits :=
  Functional.Requirements.applyTransactionCached_registry index
    (Functional.Requirements.KeyIndex.ofKeys keys) registry edits cache
#+end_src

~applyTransactionCached_registry~ proves exact published registry/error equality;
~applyTransactionCached_forget/ofRegistry~ prove complete indexed/ordinary consumer
outcomes. ~CachedPreparation.rebind~ changes only the erased alignment using an
explicit preparation equality; ~rebind_outcome~ preserves the exact certificate
or cached first-key error. ~Prepared.certify_forget~ and
~ConsumerRevision.certify_forget~ certify already prepared data without another
lookup. Generic direct rebinding still requires equality; the transaction API
discharges it automatically for negative scope.

This closes the preceding cache-view publication/rebinding gap for fixed closed
providers. It does not transport a changed dependent context/result type or
infer analytic dependencies. Full registry update construction remains even on
negative scope; earlier view-only microbenchmark numbers do not measure this
publication path. No new runtime/allocated-byte/peak-memory speedup is asserted.
Shared API/proofs cost 164 physical lines; semantic fixture 203. It checks 4096
first transactions, 3072 second transactions, nonconsumer updates, cached errors,
collisions, two contexts and six standard-only axiom reports. Runtime fixtures
use ~Claim=True~ to isolate revision plumbing; generic kernel contracts cover
arbitrary joint claims. Actual Euler migration and savings remain unmeasured.
