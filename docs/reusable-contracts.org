#+TITLE: Reusable API contracts

This guide starts from application tasks and the guarantees clients can use.
The generic Lean snippets are compiled in [[file:../Tests/ReusableContracts.lean][ReusableContracts]].
[[file:../Examples/README.org][Examples]] shows complete scenarios; this page explains how to choose and
combine reusable library interfaces.

* Choose the compilation result

| Need | Interface | Contract and cost |
|------+-----------+-------------------|
| An executable precedence | ~C4.linearize~ | Source-shaped finite compiler; returns ~Except Error (List String)~; suffix crossing can reorder an ancestor's local constraint. |
| Independent checks at each reachable node | ~C4.linearizeChecked~ | Successful output has an original ~GraphTrace~, by ~linearizeChecked_graph_sound~. |
| Retain that result with proofs for client code | ~C4.linearizeVerified~ | One checked compilation; returns ~VerifiedOrder graph root~. Proof fields erase at runtime. |
| Repeated ancestry queries | ~order.indexAncestors~ | One hash-set construction from the retained order, followed by hash-set queries. |
| Independent full graph reconstruction | ~C4.linearizeCertified~ | Ordinary compilation plus separate reconstruction; shared parent work may repeat. |

~linearizeVerified_projection~ proves exact output and error preservation
relative to ~linearizeChecked~. The new wrapper does not independently replay
the graph a second time. It validates the root's reachable declarations;
unreachable duplicate names or missing references do not become global schema
errors. None of these interfaces proves equivalence with the original
Ducournau relation. Ordinary-to-checked acceptance fails in general: the
[[file:reference-study.org::*Suffix crossing and the stronger graph contract][suffix-crossing study]] records a five-node counterexample. Use
~linearizeVerified~ when the application relies on complete ancestor-order
preservation.

* Audit an ordinary node already computed from canonical parents

Advanced clients retaining a resolver cache can use
~LinearizeState.computeAuditedNode table node~. It executes one ordinary node
merge and audits the result's uniqueness and complete parent-order
compatibility. It returns ~AuditedNode table node~, retaining the exact
ordinary execution and audit receipts. Its proof fields erase at runtime.
The audit reads parent/suffix metadata and scans the orders; it invokes no
merger. No measured speedup is claimed.

Supply ~valid : MetadataInvariant graph table~ to ~receipt.checked~ to prove
exact checked acceptance without executing checked again. With the original
node lookup ~found~, ~receipt.graphSound valid found~ recovers ~GraphTrace~:

#+begin_src lean
example (receipt : LinearizeState.AuditedNode table node)
    (valid : LinearizeState.MetadataInvariant graph table)
    (found : graph.findNode? node.name = some node) :
    GraphTrace graph node.name receipt.result.precedence
      (if node.suffix then receipt.result.precedence else
        LinearizeState.selectedTail table receipt.result.inheritedSuffix) :=
  receipt.graphSound valid found
#+end_src

~receipt.insertSound valid found fresh~ preserves canonical metadata when
inserting at a fresh node name. Starting with an arbitrary raw cache requires
its own metadata proof. An audit of an invented result is insufficient;
the retained ordinary execution receipt binds the proof to the actual result.

~computeNode_checked_iff~ characterizes single-node acceptance on canonical
parents: ordinary success, duplicate-free output, and ~ParentCompatible~
are necessary and sufficient. ~auditNode_acceptance_iff~ characterizes the
executable audit when the exact ordinary success is supplied. Audit errors
are its own diagnostics; this does not assert complete error-payload equality
with checked mode.

* Compile a whole graph through ordinary computation and audits

~linearizeAudited graph root~ resolves parents recursively from an empty cache.
Each fresh node executes ordinary computation once, followed by its audit;
shared ancestors use the retained cache. Validation, reachability, cache hits,
and fuel follow the existing resolver. No checked compiler is executed by this
API. The audit still reads and scans metadata; no measured speedup is claimed.

Successful execution establishes an original ~GraphTrace~ without caller
compatibility, metadata, or trace premises:

#+begin_src lean
example (success : linearizeAudited graph root = .ok output) :
    ∃ tail, GraphTrace graph root output tail := linearizeAudited_graph_sound success
#+end_src

~linearizeAudited_accepts_mode success true~ proves checked acceptance of the
same output; ~linearizeAudited_ordinary success~ proves ordinary acceptance.
For an advanced client starting from a canonical cache,
~resolveAuditedNode_acceptance valid success~ supplies both exact resolver
successes and the final ~MetadataInvariant~. These are successful-execution
contracts; complete error-payload equivalence is not claimed.

~resolveAuditedNode_success_iff valid~ supplies the converse as well: checked
recursion on the same canonical cache and fuel succeeds exactly when audited
recursion returns that same cache. Cached zero-fuel hits are included.

Use ~linearizeAuditedVerified graph root~ to retain a ~VerifiedOrder~ with all
existing ancestry, hash-index, ancestor-order, and suffix contracts. It runs
the audited compiler and uses erased proofs to supply checked acceptance;
it does not rerun checked compilation. Its projection theorem preserves the
audited compiler's output or error exactly. ~linearizeVerified~ continues to
provide the checked compiler and its exact diagnostics.

The ordinary compiler alone still accepts the demonstrated suffix-crossing
counterexample. The audit rejects it. A successful audited execution closes
the graph soundness path for this API, without asserting unrestricted ordinary
soundness or measured performance gains.

* Interchange audited and checked successful results

~linearizeAudited_success_iff~ proves exact success equivalence for every graph,
root, and output, without caller validity premises. A client that already has
a checked execution receipt can transfer it directly:

#+begin_src lean
example (checked : linearizeChecked graph root = .ok output) :
    linearizeAudited graph root = .ok output := linearizeAudited_checked_complete checked
#+end_src

For clients intentionally discarding failure diagnostics,
~linearizeAudited_toOption~ proves the two optional outputs equal.
The same guarantee is available after retaining a ~VerifiedOrder~:

#+begin_src lean
example : ((linearizeAuditedVerified graph root).map (·.output)).toOption =
    (linearizeChecked graph root).toOption := linearizeAuditedVerified_toOption
#+end_src

Thus choosing ordinary computation plus audits loses no checked successful
input or output. On failure, retain the original ~Except~ value if the specific
diagnostic matters: these theorems do not equate error payloads. No performance
improvement follows from success equivalence alone.

* Retain failure receipts and prove the rejection boundary

~diagnoseAudited graph root~ executes audited compilation once and returns
~Except (RejectedOrder graph root) (VerifiedOrder graph root)~. On success,
retain the existing verified queries. On failure, ~receipt.error~ is the actual
audited diagnostic and ~receipt.rejected~ retains its execution equality.
Proof fields erase. ~diagnoseAudited_projection~ recovers the original audited
output or error exactly, so this wrapper does not rewrite diagnostics.

A rejection always excludes successful verified compilation:

#+begin_src lean
example (receipt : RejectedOrder graph root) : ¬ Nonempty (VerifiedOrder graph root) :=
  receipt.noVerified
#+end_src

~receipt.checkedRejected~ supplies checked rejection, with an existential
error rather than an equal error payload. A seven-node executable witness
combines contradictory prefix orders and a complete-parent suffix crossing:
audited reports ~inconsistentOrder~ while checked reports
~suffixOrderViolation~. Their successful-output equivalence does not imply
identical diagnostic priority.

To conclude there is no original finite graph derivation, supply reachable
declaration uniqueness. A common stronger input is global name uniqueness:

#+begin_src lean
example (receipt : RejectedOrder graph root) (unique : (graph.nodes.map Node.name).Nodup) :
    ¬ ∃ output tail, GraphTrace graph root output tail :=
  receipt.noGraphTrace (LinearizeState.reachableUnique_of_global unique)
#+end_src

~linearizeAudited_graph_iff unique~ characterizes successful execution by
original graph evidence; ~linearizeAudited_rejection_iff unique~ characterizes
failure by absence of any such evidence. The uniqueness premise matters:
two identical leaf declarations admit a kernel ~GraphTrace~ via first lookup,
but validation rejects the duplicate. Preserve ~receipt.error~ when explaining
validation failures to users; do not label every rejection as absence of graph
evidence without the required premise.

* Compile once, answer graph questions later

Retain ~order : VerifiedOrder graph root~ after successful compilation.
~order.head~, ~nodup~, ~length_bound~, and ~compiled~ expose the head,
uniqueness, graph-size bound, and equality with the ordinary compiler.
~covers~ proves exact ancestry membership, including the root itself.

For occasional queries, ~order.isAncestor query~ scans the retained list.
For many queries, retain ~index := order.indexAncestors~ and use
~index.isAncestor query~. Both return a Boolean with an ~isAncestor_iff~
theorem. Neither needs another compilation or graph traversal.

#+begin_src lean
example (order : VerifiedOrder graph root) (query : String)
    (present : order.indexAncestors.isAncestor query = true) : Ancestor graph query root :=
  order.indexAncestors.isAncestor_iff.mp present
#+end_src

For a constraint declared by a reachable ancestor, use
~order.ancestor_local_order path found declared~. It proves that the ancestor's
original local order remains an ordered sublist of the retained root output.
An indexed membership receipt supplies ~path~ directly:

#+begin_src lean
example (order : VerifiedOrder graph root) (query : String)
    (present : order.indexAncestors.isAncestor query = true)
    (found : graph.findNode? query = some node) (declared : constraint ∈ node.parentOrders) :
    constraint.Sublist order.output :=
  order.ancestor_local_order (order.indexAncestors.isAncestor_iff.mp present) found declared
#+end_src

Retain ~index := order.indexAncestors~ for repeated membership queries. This
proof consumes existing evidence; it does not compile each ancestor again.

~index.decideAncestor query~ supplies ~Decidable (Ancestor graph query root)~.
Install it with a local ~letI~ when a conditional needs a proof in its true or
false branch. This decision follows the executable hash query; it does not
introduce a classical, noncomputable decision procedure.

* Query precedence and reuse its proof

Import ~LeanPoo.C4.OrderRelation~ and retain ~order : VerifiedOrder graph root~.
~order.precedes left right~ answers whether the first name occurs before the
second in this exact retained result. It scans the list once, without another
compilation or graph traversal. It is not a hash lookup; no timing improvement
is claimed. Missing names and self comparison return ~false~.

~precedes_iff~ turns a true query into ~Precedes order.output left right~,
an ordered two-element sublist. ~precedes_members~ proves that both names are
original graph ancestors. For a resolver or handler pipeline, this lets a
consumer require an earlier provider and retain the proof alongside selection.

To reuse an ancestor's comparison in a descendant on the same graph:

#+begin_src lean
example (order : VerifiedOrder graph root)
    (ancestorOrder : VerifiedOrder graph ancestor) (path : Ancestor graph ancestor root)
    (before : ancestorOrder.precedes left right = true) : order.precedes left right = true :=
  order.monotone_precedes ancestorOrder path before
#+end_src

The caller supplies two retained results, not fresh compilation executions.
The theorem uses uniqueness of their original graph derivations to identify
the ancestor result, then transports its comparison through the root's
ancestor sublist. This does not transport an order across an edited graph.

~order.local_precedes path found declared before~ transports a pair from any
reachable declaration's original constraint. ~order.inheritance_precedes~
places a reachable node before each distinct ancestor of that node:

#+begin_src lean
example (order : VerifiedOrder graph root) (reachable : Ancestor graph node root)
    (path : Ancestor graph base node) (different : base ≠ node) :
    order.precedes node base = true := order.inheritance_precedes reachable path different
#+end_src

These apply to verified checked or audited results, including retained suffix
orders. They do not certify arbitrary ordinary compiler outputs. The
[[file:reference-study.org::*Paper properties and retained order relations][paper correspondence table]] separates these order contracts from the
still-open extended precedence graph and shape-isomorphism claims.

* Move a verified order into a new name space

Import ~LeanPoo.C4.Renaming~. Use ~graph.rename rename~ when composing independently
named resolver or factory families. It maps declaration names and every parent
reference, retaining declaration order, local-row order, and suffix flags.
It does not rename application provider dictionaries or change their values;
clients must align those keys with the renamed graph.

Retain the compiled order and supply an injective name map plus global
uniqueness of the original declaration names:

#+begin_src lean
example (order : VerifiedOrder graph root) (rename : String → String)
    (injective : Function.Injective rename) (unique : (graph.nodes.map Node.name).Nodup) :
    VerifiedOrder (graph.rename rename) (rename root) := order.rename rename injective unique
#+end_src

~order.rename~ maps its output list once. Its acceptance and graph proofs erase;
it does not execute either compiler, reconstruct parents, or run an audit.
The caller must use the same function for the graph, root, and queries.
For a fixed prefix, ~fun name => prefix ++ name~ is injective by
~String.append_right_inj prefix~. Distinct prefixes alone do not prove disjointness
of arbitrary preexisting family keys; establish that separately before union.
No runtime speedup is claimed.

~rename_output~ proves the exact mapped output. ~rename_unique~ identifies any
independently compiled verified result of that renamed graph with the migrated
one. Queries also commute with the mapping, even for self or absent names:

#+begin_src lean
example (order : VerifiedOrder graph root) (rename : String → String)
    (injective : Function.Injective rename) (unique : (graph.nodes.map Node.name).Nodup) :
    (order.rename rename injective unique).precedes (rename left) (rename right) =
      order.precedes left right := order.rename_precedes rename injective unique
#+end_src

Global declaration uniqueness is a sufficient explicit premise for this
consumer operation. Existing verified compilation validates only reachable
names, so a retained result alone does not discharge that stronger premise.
A collapsing map cannot supply injectivity and may cause duplicate-declaration
validation failure. This API transports C4 orders; it is distinct from the
object-slot ~Object.Renaming~ interface.

* Preserve caller ordering and inherited tails

~order.local_order~ transports a declared root constraint into the actual
returned precedence. ~order.ancestor_order~ supplies an ancestor's complete
derived order as a sublist. ~order.ancestor_suffix~ strengthens this to a
literal suffix for an ancestor declared with ~suffix := true~.

#+begin_src lean
example (order : VerifiedOrder graph root) (found : graph.findNode? root = some node)
    (declared : constraint ∈ node.parentOrders) : constraint.Sublist order.output :=
  order.local_order found declared
#+end_src

These proofs refer to exact original declarations and every original parent
edge, even when runtime normalization removes repeated edges and empty rows.
Applications can use them for ordered handler families, resolver pipelines,
or inherited specifications without reproving the C4 merge algorithm.

* Assemble context-dependent mathematical factories

Import ~LeanPoo.Functional.Assembly~. A ~Factory Context Result~ is
~(context : Context) → Result context~. A ~Provider Context Key Value~
maps a typed capability key to an optional factory. The result type can
include data and witnesses depending on the supplied context.

~Functional.assemble order providers~ chooses the first provided factory for
each key in the verified precedence. Selection returns function values; it
does not invoke factories. Resolve a capability once, retain that function,
and apply it to each context where its type permits. Missing capabilities
remain ~none~. ~assemble_origin~ proves the selected provider is an original
graph ancestor. ~apply_selected~ proves application uses the exact selected
function and supplied context.

Use one ~Context~ for mutually dependent source data, radius choices, and
their proof witnesses. Give the value family the type ~Context → Key → Type~.
If changing a parameter changes the required theorem, the factory must supply
the witness at the new indexed type. C4 selection supplies precedence and
provider provenance; the mathematical contract comes from this result type.
It does not automatically transport proofs across changed data.

For a required capability, use ~Functional.require provider key~ during
preparation. Match its ~Except~ once: ~.error key~ identifies the missing
capability and ~.ok build~ supplies a retained factory. Later calls to
~build context~ perform no provider lookup. ~require_ok_iff~ turns a successful
preparation receipt into ~provider key = some build~; combine it with
~assemble_origin~ to recover the original graph provider.

~Factory.zipWith combine left right~ invokes retained factories at the same
context and passes their data and witnesses to ~combine~. The result may be
a client's dependent record. ~Factory.reindex project build~ adapts a factory
to a larger context; the result is ~Result (project outer)~, preserving its
exact dependency. Supplying a fixed old witness where a new context requires
a different witness is still rejected by Lean.

The [[file:use-cases/navier-stokes-euler.org][Euler budget study]] identifies actual upstream factory call sites.
[[file:../Examples/ContextualFactories.lean][ContextualFactories]] shows the provider boundary with arbitrary
context-indexed mathematical types, a residual-only override, and a
~Prepared~ consumer retaining its required background/residual functions.
The external Euler repository supplies design references; no import or
build dependency is introduced.

* Prepare a typed capability checklist once

Import ~LeanPoo.Functional.Requirements~. Declare the capabilities needed by
one consumer as a ~List Key~. ~Requirements.prepare provider keys~ returns
~Except Key (Requirements.Factories Context Value keys)~. The tuple follows
the caller's key order; each component has its own context-indexed result
type. Empty lists succeed, and repeated keys retain repeated selected functions.
The first missing key is reported before any factory is invoked.

After matching success once, retain the tuple and call
~Requirements.build (keys := requested) retained context~ for every compatible
context, where ~requested~ is the checklist used for preparation. It returns
~Requirements.Results Value context keys~, a heterogeneous tuple indexed by
exactly that context and checklist. The builder adds no provider lookup or graph compilation; supplied factory
bodies keep their own behavior. Pass the results to your existing constructor; mathematical guards
and witnesses remain part of its own types.

~prepare_ok_iff~ proves the tuple's ~Selected~ contract: every component is
exactly the provider's selected function. ~Selected.available~ exposes this
for any requested key. ~prepare_origin~ combines it with a verified C4 order
and proves original-graph ancestry for every requested capability. These
contracts are generic over arbitrary key and context/result types.

[[file:../Examples/ContextualFactories.lean][ContextualFactories.Prepared]] now uses this library tuple instead of a
consumer-owned preparation record and repeated ~require~ statements. Changing
the checklist changes its type as well; adapt the consumer's constructor to
the new fields. This API removes repeated preparation plumbing, not the
consumer's domain-specific construction or analytic proof obligations.

* Preserve selected factories across provider-family renaming

~Functional.select_rename~ equates selection on mapped names when each mapped
provider agrees with the original provider on the requested key. Agreement is
needed only on the retained precedence. ~assemble_rename~ lifts that contract
to ~VerifiedOrder.rename~: supply the injective map, original global declaration
uniqueness, and provider agreement on original graph ancestors.

Graph renaming alone cannot rename a String-indexed provider dictionary.
Store the same factory values under the new names. If that alignment is
missing, selection can return a missing capability or a different factory;
the theorem requires the alignment explicitly. Capability keys and mathematical
contexts do not change. With it, selected functions agree exactly, so the
existing requirement tuple and consumer proofs remain reusable.

[[file:../Tests/FunctionalRequirements.lean][FunctionalRequirements]] compiles both generic provenance and renaming
clients, checks 192 preparation cases with heterogeneous result types, and
checks an aligned namespace prefix against independently compiled renamed
C4 output. A deliberately unaligned dictionary fails preparation.

* Reuse proofs after an unrelated change

~Proof.Obligation~ declares a predicate and the dependencies sufficient to
transport its proof. ~Patch.frame~ proves that untouched keys retain their
values. ~Proof.reuse~ combines those existing contracts:

#+begin_src lean
example (current : ProofObject Key Value) (update : Patch Key Value)
    (certificate : Certificate current) (obligation : Obligation Key Value)
    (owned : obligation ∈ current.obligations) (safe : unaffected obligation update) :
    obligation.holds (append current update).state :=
  reuse current update certificate obligation owned safe
#+end_src

~Proof.close~ builds the next certificate from the old certificate plus
proofs for affected old obligations and newly added obligations. The stability
and dependency contracts are premises, not facts inferred from a function's
source code. A change to viscosity, geometry, or forcing may affect many
obligations and cannot be certified as unrelated merely by choosing a new
provider name.

For several writes, ~Patch.setMany~ preserves dependent key types and uses
last-write semantics. ~Patch.setMany_last~ exposes that guarantee.
~CertifiedObject.applyRevision~ connects this proof workflow to the object's
checked finite change footprint when the caller supplies its resolver
alignment and discharges the pending obligations.


* Keep a prepared checklist stable across unrelated edits

~Requirements.prepare_congr provider other keys same~ proves exact equality
of preparation results when the providers agree on the requested keys.
Unrequested keys require no agreement. Both retained function tuples and
first-missing errors are preserved. This is a contract about provider values;
it does not inspect arbitrary factory bodies to infer their stability.

~Requirements.prepare_rename~ preserves the whole checklist through verified
graph renaming, with alignment needed only on requested keys at original
ancestors. It combines ~assemble_rename~ with ~prepare_congr~ and preserves
errors as well as successes. Namespace alignment remains a caller obligation.

[[file:../Tests/FunctionalMaintenance.lean][FunctionalMaintenance.same_client]] proves a five-field manual provider
client and the general checklist API return exactly the same function or
first missing error. The [[file:use-cases/euler-maintenance-checklist.org][Euler maintenance report]] gives reproducible local
code counts, actual reference repetitions, and shared/adapter cost boundaries.


* Access prepared factories by typed key

Import ~LeanPoo.Functional.Access~ and derive or supply ~DecidableEq Key~.
After a successful preparation, use
~Requirements.factoryAt (keys := requested) retained key member~. The proof
~member : key ∈ requested~ excludes a missing key and the return type is the
factory for that exact key. Literal lists usually discharge membership with
~by simp [requested]~. Repeated keys use their first tuple occurrence.

Retain this returned function before repeated context calls. Named access
scans the checklist; it is not a constant-time field offset. It invokes no
factory during the scan, and subsequent calls invoke the retained factory's
own body. A consumer no longer embeds positions such as ~.2.2.1~.

~factoryAt_selected~ gives ~provider key = some (factoryAt ...)~ from the
selected-tuple contract. ~factoryAt_stable~ proves named factory equality for
any two successful checklists from that provider containing the key. A newly
missing required key can still fail preparation. ~factoryAt_origin~ exposes
the exact original C4 ancestor supplying this function after verified assembly.

[[file:../Examples/ContextualFactories.lean][ContextualFactories.Prepared.build]] now extracts background and residual
by key, then retains them in ~Factory.zipWith~. Membership proofs and user
constructors still need to follow their capability types. This is a maintenance
contract, not a measured resolver throughput improvement.

* Adapt existing proposition-valued theorems

~Factory.fromProof prove~ accepts ~prove : ∀ context, Claim context~ for
~Claim : Context → Prop~ and returns ~Factory Context (fun c => PLift (Claim c))~.
Its result's ~down~ is a proof of the exact supplied context's claim;
~fromProof_down~ is definitionally equal to the existing theorem call and
requires no axioms. This bridges the result sort without rewriting analytic
proofs. Context/guard binding and noncomputable source behavior remain caller
responsibilities.

* Declare only the capabilities a consumer uses

Import ~LeanPoo.Functional.View~. Give the consumer a type
~Requirements.Factories Context Value needs → Result~ where ~needs~ lists its
actual dependencies. Keep source-list positions, provider registry, and graph
outside that function. For independent consumers, call ~prepare provider needs~
directly: a missing unrelated capability must not become a global startup gate.

When a larger family has already been prepared, call
~Requirements.project retained needs included~, with
~included : ∀ key ∈ needs, key ∈ source~. The result has the consumer's exact
list and dependent result types. Projection can reorder or repeat keys and
runs no factory or provider lookup. It scans the source once per requested key;
retain the projected tuple before repeated context calls. It neither generates
adapters nor removes source capabilities.

~project_selected~ preserves the selected-function contract, so original C4
provenance remains available through ~factoryAt_origin~ and ~project_ready~.
~project_ready~ proves agreement with independent local preparation.
~project_stable~ compares different successful source lists and different
providers, requiring function equality only for ~needs~. The two lists may
contain different unrelated capabilities. ~consumer_stable~ transfers exact
results of any function using this narrow interface. Results can themselves be
functions over all contexts; equality also transports an existing proposition
about the result, as compiled in [[file:../Tests/FunctionalView.lean][FunctionalView]].

The contract fixes ~Context~, ~Key~, and ~Value~. Changed requested functions,
changed proposition statements, and changed context/result types require new
compatibility evidence. Equality of functions is sufficient and can be proved
extensionally; observational similarity alone does not discharge that premise.
This prevents unrelated source edits from requiring consumer-expression or
consumer-theorem changes under the stated conditions. It does not stop Lean
from recompiling modules whose imports changed, nor establish an elapsed-time
improvement.

* Preserve an observation interface across representation changes

Import ~LeanPoo.Functional.Observation~ when implementations expose different
representation types but share a public semantic interface. Declare
~Observed : Context → Key → Type~, with two maps
~expose : ∀ c k, Value c k → Observed c k~ and
~reveal : ∀ c k, Other c k → Observed c k~. Give consumers only the observed
factories. Values, representations, and contexts remain explicitly indexed;
the library does not select a suitable observation for the application.

~Requirements.Related relation keys left right~ records pointwise compatibility
of retained functions, allowing different original result families.
~RelatedOn provider other needs relation~ declares this condition only for
selected pairs of factories on ~needs~. It does not imply availability or
missing-key error equivalence. ~project_related~ derives related narrow views
from two successful preparations, with only the declared keys in its premise.
It also handles distinct source lists and repeated consumer keys.

~Requirements.observe expose retained~ constructs the public factories without
invoking the original factories or the observation map. Invocation later runs
the original function and its map. Observation can have a cost; retain these
public factories before repeated use. No observation is memoized or assumed
constant-time. If the two maps yield equal observations at every supplied
context, ~observe_congr~ proves the public factory tuples equal and
~observed_consumer_stable~ preserves any consumer result. This includes results
that are themselves context functions and transfers propositions about them.
The [[file:../Tests/FunctionalObservation.lean][compiled test]] exercises distinct representations, dependent guards, a deleted
unrequested capability, reordered source lists, and repeated consumer keys.

Only exposed observations are preserved. A claim about hidden metadata cannot
be transferred from equality of paths alone. If a consumer needs a bound or
proof witness, expose the relevant property or prove its relationship to the
observation explicitly. The test rejects a changed public value and use of a
witness from a different context. Context/key/public observation type changes
still need explicit typed adapters. Original C4 selections need not be equal;
the selected implementations must satisfy the stated pointwise relation.

The Euler reference already contains a path-to-field-tower bridge. Reusing it
as compatibility evidence would be application-owned; no external adapter or
large-library migration has been compiled here. See the [[file:use-cases/euler-maintenance-checklist.org][research checklist]].

* Retarget existing evidence to equal replacement data

Import ~LeanPoo.Functional.Transport~. After establishing equality of the data
produced by two implementations, ~Factory.transport~ reuses an existing witness
family and gives it the exact replacement index:

#+begin_src lean
example {Context : Type} {Data : Context → Type}
    (Certificate : (c : Context) → Data c → Type)
    (old new : Functional.Factory Context Data)
    (same : ∀ c, old c = new c)
    (existing : Functional.Factory Context (fun c => Certificate c (old c))) :
    Functional.Factory Context (fun c => Certificate c (new c)) :=
  Functional.Factory.transport Certificate same existing
#+end_src

The witness may be a record containing data, proof fields, and further
quantified obligations. Its implementation is retained. ~transport_refl~
preserves identity, ~transport_trans~ equates chained and direct migration,
and ~transport_roundtrip~ restores the exact original witness family after
migration back. These laws apply to arbitrary dependent witnesses.

For an existing theorem ~prove : ∀ c, Claim c (old c)~, call
~Factory.transportProof Claim same prove~ to obtain ~∀ c, Claim c (new c)~.
It returns Prop directly and requires no axioms. If a Type-valued proof factory
is required by a provider, wrap the result with ~Factory.fromProof~. No analytic
proof is synthesized: the old theorem and the data equality remain prerequisites.

The observation pipeline supplies that equality. If a consumer returns a data
factory, ~observed_consumer_stable~ gives equality of the old and replacement
data factories. Use ~fun c => congrFun dataEqual c~ as the transport premise.
The [[file:../Tests/FunctionalTransport.lean][generic compiled client]] connects these APIs without assuming identical
original representation types. This factors the common migration step out of
individual analytic consumers.

Transport fixes the context and the entire datum indexed by the witness.
Equality of one projected field cannot retarget evidence indexed by a larger
unequal record. Changed context types, changed claims, or merely ordered/
approximately equal data require an explicit application-specific adapter or
proof. The retained witness body keeps its original computation; this API does
not remove legacy computations or establish a runtime improvement. The
[[file:use-cases/euler-maintenance-checklist.org][reference research checklist]] records an existing Euler data-equality rewrite
with the same dependent-index shape, without claiming an external migration.

* Reuse a capability family in an extended context

Import ~LeanPoo.Functional.Reindex~. Supply one explicit
~project : Outer → Context~ containing the complete old dependent context.
~reindexProvider project provider~ adapts every available factory; selection
and missing capabilities remain independent of context values. ~select_reindex~
and ~assemble_reindex~ preserve first-provider selection and reuse the same
verified C4 order. No new graph compilation is required.

#+begin_src lean
example {Context Outer Key : Type} {Value : Context → Key → Type}
    (project : Outer → Context) (provider : Functional.Provider Context Key Value)
    (keys : List Key) :
    Functional.Requirements.prepare (Functional.reindexProvider project provider) keys =
      (Functional.Requirements.prepare provider keys).map
        (Functional.Requirements.reindex project) :=
  Functional.Requirements.prepare_reindex project provider keys
#+end_src

Alternatively retain a successful checklist once and call
~Requirements.reindex project retained~. ~prepare_reindex~ proves these paths
agree, including empty/repeated lists and the exact first missing key. Users
keep one declaration of their capability checklist instead of writing one
~require~ and one context wrapper per capability.

~Requirements.projectedResults project keys outer~ converts the adapted tuple
into its original type at ~project outer~. Abstract recursive tuple types need
this proved type equality; no element traversal or factory invocation is added
by the cast. ~build_reindex~ proves the result is exactly the original
~Requirements.build retained (project outer)~, including dependent proof fields.
An existing proof consumer can be lifted with ~Factory.reindex project~ and
keeps precisely its old claim at the projection.

Adaptation constructs function wrappers; invocation computes the projection
for each invoked factory and retains the old computation. It is not caching.
The caller owns the projection, including old guards, dependent fields and
implicit instances. Added fields do not imply new claims, changed legacy data
or changed theorem statements. The [[file:../Tests/FunctionalReindex.lean][compiled client]] rejects both a witness at
a different legacy context and a claim about an unrelated new field. Reindexing
neither proves equality between different analytic constructions nor establishes
a speedup. See the [[file:use-cases/euler-maintenance-checklist.org][reference checklist]] for the resulting research boundary.

* Reuse verified orders after registry declaration reordering

Import ~LeanPoo.C4.Presentation~ and ~LeanPoo.Functional.Presentation~.
Keep each node's exact name, local parent rows and suffix flag. Supply
~same : graph.nodes.Perm other.nodes~ and
~unique : (graph.nodes.map C4.Node.name).Nodup~. The permutation concerns the
outer declaration list; reordering a node's parent rows can change precedence.

#+begin_src lean
example {Context Key : Type} {Value : Context → Key → Type}
    {graph other : C4.Graph} (order : C4.VerifiedOrder graph root)
    (same : graph.nodes.Perm other.nodes)
    (unique : (graph.nodes.map C4.Node.name).Nodup)
    (providers : String → Functional.Provider Context Key Value) (keys : List Key) :
    Functional.Requirements.prepare
        (Functional.assemble (order.permute same unique) providers) keys =
      Functional.Requirements.prepare (Functional.assemble order providers) keys :=
  Functional.Requirements.prepare_permute order same unique providers keys
#+end_src

~VerifiedOrder.permute~ retains the existing output list without mapping it or
running either resolver. ~permute_unique~ identifies the output of any fresh
verified compilation. ~linearizeChecked_permute_ok~ proves exact successful
checked outputs in both directions, including that a rejected graph cannot
become accepted under these premises. It does not equate error payloads:
validation reports its first invalid reference in declaration-list order.

~assemble_permute~ preserves the whole provider dictionary, and
~Requirements.prepare_permute~ preserves exact functions and first missing
capability errors for any checklist. Apply ~congrArg~ to reuse any downstream
consumer result or result proposition; there are no per-key ~require~ rewrites.
Provider names, context, keys and dependent result types remain unchanged.
No factory is invoked by retained-order migration.

The caller must establish the permutation and uniqueness evidence; the library
does not infer equivalence of edited declarations. Duplicate names can change
first lookup when reordered and are outside this guarantee. The more general
~Graph.SameLookup~, ~GraphTrace.represent~ and ~VerifiedOrder.represent~ APIs
accept explicit complete lookup agreement; the target must have unique names
for checked acceptance. This exact-lookup condition includes absent names and
is stronger than a consumer-specific reachable equivalence.

See [[file:../Tests/C4Presentation.lean][the compiled generic consumer and corpus]] and the [[file:use-cases/euler-maintenance-checklist.org][reference checklist]].
These contracts preserve semantic consumers under registry restructuring;
Lean module recompilation, error diagnostic order, changed local precedence,
net source savings and elapsed-time improvement are separate measurements.

* Combine label changes and declaration reordering

Import ~LeanPoo.C4.Relabeling~ and ~LeanPoo.Functional.Relabeling~.
~Graph.Relabeling graph other~ packages ~rename~, its global injectivity proof,
and ~declarations : (graph.rename rename).nodes.Perm other.nodes~. This witness
preserves exact parent rows and suffix flags after name mapping. It does not
infer a mapping from similar-looking graphs or align provider dictionaries.

#+begin_src lean
example {graph other : C4.Graph} (order : C4.VerifiedOrder graph root)
    (rename : String → String) (injective : Function.Injective rename)
    (declarations : (graph.rename rename).nodes.Perm other.nodes)
    (unique : (graph.nodes.map C4.Node.name).Nodup) :
    C4.VerifiedOrder other (rename root) :=
  order.relabel ⟨rename, injective, declarations⟩ unique
#+end_src

~change.unique~ transports source name uniqueness to the target.
~VerifiedOrder.relabel~ maps the retained output once and invokes no resolver.
~relabel_unique~ identifies any freshly verified target output, and
~relabel_precedes~ preserves mapped pair queries, including absent/self queries.
For multiple migrations, compose witnesses with ~first.trans second~ and migrate
once. ~relabel_trans_output~ proves equality with sequential migration. The
direct path avoids building and traversing an intermediate output list; the
composed name function still evaluates both name transformations. This is a
structural allocation/pass boundary, not an elapsed-time benchmark.

~assemble_relabel~ preserves a requested factory when providers align under
~change.rename~ on original ancestors. ~Requirements.prepare_relabel~ lifts
that condition to the complete caller checklist, including exact functions
and the first missing key. Its alignment premise is required only for keys
in the checklist; unrelated capabilities and unrelated graph names need no
alignment proof. A generic consumer and its existing result proposition use
this equality through ~congrArg~ or rewriting, with no per-key ~require~ edits.
The context, keys and dependent result families remain fixed.

Provider alignment is essential: the [[file:../Tests/C4Relabeling.lean][compiled client]] shows an entry becomes
missing if the graph is renamed but the old dictionary is kept. Applications
own mapping construction, provider adapters, injectivity, exact declaration
permutation and source uniqueness. Global injectivity is an explicit sufficient
premise, stronger than injectivity merely on declared nodes. This API does not
prove arbitrary finite graph-isomorphism extension, changed local parent orders,
new analytic claims, or equal error diagnostic payloads. See the [[file:use-cases/euler-maintenance-checklist.org][cost checklist]].
