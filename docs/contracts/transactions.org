* Apply a normalized capability batch directly to a shared registry

Import ~LeanPoo.Functional.RegistryBatch~. Call ~registry.patchBatch name edits~
with the same typed ~CapabilityEdit~ list used by ProviderOverlay. The API
checks the provider name once, compiles a normalized overlay over its retained
original provider, and installs it with one insertion. No handwritten dictionary
branch, provider-alignment proof, graph declaration fold or factory invocation
is needed. Unknown names return that exact name as error, including an empty
batch. Known-name empty batches retain all original dictionary functions.

A successful batch preserves provider-name membership, every other provider's
entire function, and every unedited key even at the target provider. Later
same-key edits win; explicit removal stays distinct from base fallback.
~patchBatch_dictionary~ supplies whole-dictionary equality to the sequential
single-provider reference. This is equality of selected functions at all
contexts, not physical hash-table identity or a new mathematical equivalence
between unrelated factories.

Retain each root's ancestry index once. Query
~Requirements.batchMayAffect index keys name edits~ for each consumer. False
means either the provider is outside that root or its requested key list is
disjoint from the batch footprint. Use ~prepare_patchBatch_of_unaffected~ to
reuse exact prepared tuples, first errors and arbitrary consumer claims by one
rewrite. The generic compiled client in FunctionalRegistryBatch requires no
per-key ~require~ or untouched-provider alignment proofs. The explicit
~prepare_patchBatch_stable~ theorem also accepts the negative scope premise.
A true query is conservative: earlier providers or missing keys may hide edits.

#+begin_src lean
def update {Context Key : Type} [DecidableEq Key] {Value : Context → Key → Type}
    (registry : Functional.ProviderRegistry Context Key Value)
    (name : String) (edits : List (Functional.CapabilityEdit Context Key Value)) :=
  registry.patchBatch name edits
#+end_src

The registry operation makes one name lookup/insertion for an entire batch,
versus one per edit for repeated known-name ~registry.patch~ calls. The local
256-edit same-key case therefore has one rather than 256 lookup/insertion
operations by definition, and its normalized overlay has one override. This
is structural operation-count evidence; no elapsed-time or allocated-byte gain
has been measured. Compilation still filters/allocates lists and can be
quadratic with all-distinct keys. A batch impact query scans the original edit
list and requested keys. Persistent hash storage may copy under sharing.

Normalization covers the supplied batch. Applying another batch over an already
patched provider retains that prior provider as its base, so repeated batches
can accumulate base-overlay layers. Keep a saved original registry/provider
and compile the complete intended history when that preservation policy fits
other changes. The API does not collapse arbitrary old closures, provide a
multi-name transaction or infer analytic dependency closure. Graph/order and
context/key/result families remain fixed. Euler adapters and actual maintenance
savings remain unmeasured.

* Multi-provider pure transactions and whole-consumer reuse

~RegistryEdit~ packages a provider name with its heterogeneous typed batch.
~ProviderRegistry.patchTransaction registry changes~ processes the list in caller
order. Empty transactions return the original registry; repeated names apply
sequentially and later same-key writes win. The first unknown name, including
an empty batch at that name, returns an error with no partial registry in the
result. The retained original snapshot remains usable after success or failure.
This is return-value atomicity, without external effects or concurrent isolation.

Retain each consumer's ancestry index and requested keys. A false
~Requirements.transactionMayAffect index keys changes~ plus successful execution
lets ~prepare_patchTransaction_of_unaffected~ rewrite the entire preparation.
The same old arbitrary consumer claim is then reusable without handwritten
per-provider alignment or repeated per-key ~require~. False does not make an
invalid transaction succeed. True is only a candidate: shadowing, earlier missing
keys and edits later restored can make a candidate observationally unchanged.

#+begin_src lean
def changeMany {Context Key : Type} [DecidableEq Key] {Value : Context → Key → Type}
    (registry : Functional.ProviderRegistry Context Key Value)
    (changes : List (Functional.RegistryEdit Context Key Value)) :=
  registry.patchTransaction changes
#+end_src

The kernel sequencing law ~patchTransaction_cons~ preserves exact first-error
behavior; ~patchTransaction_missing~ proves head-name rejection and
~patchTransaction_scope~ preserves membership for successful transactions.
No new graph compilation, provider acquisition or factory invocation occurs.
Each reached named batch costs one lookup and each successful batch one
insertion, plus normalization and possible persistent-storage copies. Work on a
valid prefix is still performed before a later failure. Repeated names are not
grouped and may accumulate base overlays. Candidate queries scan explicit
histories; no measured runtime gain or precise analytic dependency closure is
claimed. Context/key/result families and graph/order remain fixed.

* Retained indexed capability state

~IndexedOverlay~ keeps the original provider and a dependent hash table of typed
optional factories. A missing entry delegates to base; a stored ~none~ explicitly
removes that capability. ~set~ inserts one typed cell. ~extend~ updates a retained
state with caller-ordered edits and preserves its original base. Keep that state
between batches instead of rebuilding an overlay over its materialized provider.
Later same-key writes overwrite the cell. Already wrapped input bases are not
compacted.

~set_provider~ and ~extend_provider~ prove exact sequential ~patchKey~ semantics.
~compile_provider~ equates the entire provider function with the existing list
overlay; ~prepare_indexed_extend~ and ~prepare_indexed_compile~ lift this to whole
consumer tuples and first errors. The generic arbitrary-claim client uses a
single rewrite, without per-key ~require~ or alignment. ~extend_append~ proves
that successive extensions equal one concatenated extension, including state,
and ~extend_base~ proves that the retained base is unchanged.

#+begin_src lean
def continueEdits {Context Key : Type} [BEq Key] [Hashable Key] [LawfulBEq Key]
    [DecidableEq Key] {Value : Context → Key → Type}
    (state : Functional.IndexedOverlay Context Key Value)
    (changes : List (Functional.CapabilityEdit Context Key Value)) :=
  state.extend changes
#+end_src

Use ~state.provider~ with the existing assembly/preparation APIs; retain prepared
factories when queries can be moved out of a repeated consumer loop. Hash/equality
instances are explicit. The list implementation remains useful without a hash
instance and for small tables. Hash lookup/insertion replaces full list scans;
collisions, resizing, retained hash copies and base costs remain. There is no
unconditional constant-time guarantee or automatic graph/type/dependency rewrite.
The paired performance receipt isolates construction and direct queries under
the Lean interpreter; it excludes imports, graph/registry/preparation costs and
Euler proofs. Semantic tests force all keys to collide. Euler migration and net
maintenance savings remain unmeasured.

* Indexed state retained inside the provider registry

Convert an existing scoped registry once with ~IndexedRegistry.ofRegistry~.
The named table now stores ~IndexedOverlay~ states rather than only materialized
provider functions. ~patchBatch name edits~ extends that name's retained state,
so arbitrarily many calls preserve the original base. Unknown names, including
empty batches, are errors. Other names and declared-name membership remain
unchanged. Initial conversion maps entries; each successful batch performs one
name lookup/insertion plus indexed cell writes, without a graph fold or factories.

Use ~registry.dictionary~ directly with ~assemble~ and ~Requirements.prepare~.
No extra table is constructed in that query path. ~snapshot~ materializes a
~ProviderRegistry~ for older APIs requiring that concrete type, and traverses
all entries; keep it out of repeated queries. ~ofRegistry_dictionary~ and
~snapshot_dictionary~ establish exact whole-function agreement.

#+begin_src lean
def continueNamedEdits {Context Key : Type} [BEq Key] [Hashable Key]
    [LawfulBEq Key] [DecidableEq Key] {Value : Context → Key → Type}
    (state : Functional.IndexedRegistry Context Key Value) (name : String)
    (changes : List (Functional.CapabilityEdit Context Key Value)) :=
  state.patchBatch name changes
#+end_src

The practical workflow is: retain verified root/ancestry indexes and consumer
key lists; convert the registry once; check the returned ~Except~ at every update;
use the new dictionary directly; reuse consumers for which ~batchMayAffect~ is
false via ~prepare_indexedRegistry_of_unaffected~. That theorem internally proves
the ordinary batch correspondence. Users do not construct comparison snapshots,
write per-name alignment lemmas or repeat per-key ~require~ proofs.

~patchBatch_agreement~ equates the whole updated dictionary to an ordinary batch
on the old snapshot. ~patchBatch_base~ preserves bases at every name, including
the edited one. The ordinary batch's sequential semantics, repeated-key last
write and removals therefore transfer exactly. The tests check old snapshots,
base retention, first errors and independent consumer results with colliding keys.

For atomic multi-name changes, import ~Functional.IndexedTransaction~ and use
~registry.patchTransaction changes~ as described below. Individual batch calls
still have separate results and expose prior successful states on later errors.
Hash
collisions/resizing/shared copies, base costs and conservative footprint scans
remain. Retaining an already wrapped input base does not compact it. Performance
of named updates is measured separately from standalone overlay measurements;
the earlier interpreter-only receipt supports no graph/Euler proof or native-code
speedup claim. The later native/lifetime study below has its own local scope.

* Choosing representation with native and retained-state evidence

The existing list/indexed APIs keep the same typed semantics. The performance
study now exposes ~--engine native~ and ~--policy retained~ so a caller can check
its actual execution engine and lifetime policy. Retained native repeated-batch
query medians are 4.868/0.160 ms for list/indexed; update medians are
0.306/0.266 ms. Same-source interpreter updates still regress, and native latest
updates are slightly slower for indexed state. Tiny small-table timings vary.
Choose based on caller workloads; there is no automatic/global switch threshold.

The native executable is built by the complete gate. Four admission cases check
current cells and retained old observations under both representations/policies.
Performance thresholds are excluded from CI. This strengthens execution evidence
for the existing ~patchBatch/dictionary~ APIs and their kernel contracts; it does
not change graph/type/dependency premises or infer Euler proof equivalence.
