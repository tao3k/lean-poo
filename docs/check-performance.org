#+TITLE: Check pipeline performance

* Preserve the complete gate

~just check~ enters one Lake environment, builds the complete public library
once, checks C4's source-owned types, and runs 110 independent example/contract
files with four workers, followed by four bounded diagnostic files and Org
documentation. The source commands live in the Justfile; the Python runner
reads the two canonical recipes through ~just --dump --dump-format json~ and
CI does not maintain a second file list. Standalone public
~check-*~ recipes retain their build prerequisites. The full gate avoids their
repeated build traversals and six repeated prototype examples.

No unique Lean source, proof, axiom report, or diagnostic check is removed.
The current gate covers 114 unique example/test files, including the typed
requirement corpus. The earlier 104-file inventory remains covered. Existing memory/allocation
limits, 30-second bounded checks, and the expected two-second unbounded-body
rejection remain unchanged. This changes orchestration; it does not establish
that C4's compilation algorithm became faster.

The diagnostic dispatcher explicitly supplies ~false~ to both optional
~verbose~ parameters. Without those arguments, ~just~ consumes the following
~check-proof-reuse~ recipe name as ~check-incremental~'s parameter and omits that
check. The earlier source inventory alone did not establish execution of all
114 files. The corrected dispatcher runs the bounded proof-reuse corpus too;
the prior successful gate is not complete evidence for that diagnostic.

* Atomic CI and its merge gate

The ~library~ job builds the public library and proofs. Its compressed build
artifact is named with the current workflow SHA and passed only within that
run. Twelve file-shard jobs each consume it and check nine or ten files. The
matrix has ~max-parallel: 12~ and ~fail-fast: false~; an independent ~diagnostics~
job consumes the same artifact. Including library, docs and the aggregate,
the workflow has sixteen jobs. The ~docs~ job installs only the Org
parser and runs independently of Lean. Each job has a bounded timeout.

The ~check~ job retains the previous status name and runs even after failure.
It requires ~success~ from the library, all twelve shards, diagnostics and docs; failed,
cancelled, and skipped prerequisites cannot pass. No path filters skip checks.
The local pre-commit hook still requires the complete ~just check~ gate.

The recipes can be reproduced after ~lake build~:

#+begin_src sh
lake env python3 tools/check_atoms.py --jobs 4
lake env python3 tools/check_atoms.py --shard 0 --shards 12 --jobs 1
lake env just --set lean lean _check-diagnostics
just check-docs
#+end_src

Artifact transfer and runner setup have costs. The earlier single-job Linux
check took 113 seconds at commit ~2abf644~; compare exact new-run job/critical
path timings before claiming an overall CI speedup. Parallel jobs improve
failure localization even when setup dominates wall time.

The shard partition is deterministic and exhaustive over the canonical recipe
rows. Python admission tests require nonempty shards, exact once-only coverage,
unchanged bounded command arguments, and nonzero status for real child failure,
timeout and launch error. Unsupported recipe expressions and unknown or empty
selections fail. Each process emits a file start, actual Lean output, and a
completion with status and elapsed time; no progress heartbeat is synthesized.
Failure output stays attributed to its file. Interrupting the runner stops its
active process groups and prevents pending files from launching.

Lean's internal parallel work does not make separate shell invocations run
concurrently. The corrected serial complete gate on this host took 1085.70 s
wall and 115.04 s CPU. This exposes a large wall/CPU gap but does not identify
its operating-system or host cause. Four independent workers remove the
file-by-file scheduling dependency; CI schedules twelve shards after the
library is ready. GitHub runner availability and artifact/setup costs still
bound the actual concurrency and end-to-end improvement.

The [[file:../Benchmarks/receipts/check-atoms-2026-10-05.json][paired atom study]] runs the same eight warm Lean files with one and four
workers, alternates order over two repetitions, and requires exact per-file
Lean transcript hashes and source identity. Its schema remains 1. The study
excludes library preparation, remaining files, diagnostics, docs and CI runner
queues; it cannot establish a full-gate or CI speedup by itself.

| Same eight warm Lean files | Wall median (s) | CPU median (s) |
|---------------------------+-----------------+----------------|
| One worker | 94.236 | 9.247 |
| Four workers | 26.790 | 8.746 |

The two paired repetitions preserve per-file output hashes and source hashes.
For this selected corpus the wall median is 3.52 times faster (71.6% less wall
time). CPU time remains similar. This supports parallel scheduling of these
independent files; it is not a Lean kernel or C4 algorithm speedup claim.

* Controlled warm startup measurements

Run ~just benchmark-check-startup~ or save the full receipt:

#+begin_src sh
python3 Benchmarks/CheckStartup.py --repeats 3 --output /tmp/check-startup.json
#+end_src

The stdlib-only Python harness runs variants sequentially and alternates their
order. Six identical cached module targets compare separate Lake invocations
with one batched invocation. Two identical Lean files compare per-file Lake
launches with the same native Lean executable in an already configured
~LEAN_PATH~. The latter transcripts must match exactly. Every command must
succeed within 30 seconds; a timeout or changed transcript fails the study.
The initial warm build and shared-environment setup are separate preparation
costs, recorded outside the timed samples.

The [[file:../Benchmarks/receipts/check-startup-2026-10-04.json][2026-10-04 receipt]] retains every sample, preparation time, selected inputs,
and source hashes. Medians from three repetitions on this host:

| Selected workload | Baseline wall s | Shared wall s | Baseline CPU s | Shared CPU s |
|-------------------+-----------------+---------------+----------------+--------------|
| Six cached builds | 2.181 | 0.210 | 0.338 | 0.065 |
| Two Lean checks | 16.320 | 14.770 | 1.910 | 1.724 |

The first row reduces measured wall time by about 90% and CPU time by 81%.
The second reduces measured wall time by about 9.5% and CPU time by 9.7%,
excluding the separately reported one-time environment preparation. The full
gate amortizes preparation over all checks. These samples do not establish a
whole-suite percentage or cold-build improvement.

The baseline full pre-commit gate took about thirteen minutes on this busy
host. In these samples wall time is much larger than CPU time, so waiting and
resource contention contribute materially. CPU and wall time must remain
separate; a different host load can change full-gate wall time. Lean's thread
policy is unchanged. Local full-gate and exact-head CI receipts remain required.

* Keep runtime performance distinct

~just benchmark-c4~ measures chain and fan-in compilation at 32–256 nodes.
Declaration, schema merge, memoization, revision, dispatch, layout, and mutable
prototype benchmarks have their own recipes. Use unchanged inputs, semantic
checks, and repeated A/B measurements before changing those algorithms.
Startup improvements cannot be reported as runtime factory or resolver gains.
