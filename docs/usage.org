#+TITLE: LeanPoo API usage

The object workflow is in [[file:use-case.md][the PO use case]].
This page is a compact map of the current Lean API.

* Build an object

~Prototype.Proto~, ~compose~, and ~instantiate~ are the POOF starting point.
~Prototype.Generator~ keeps an inherited computation open, while
~Prototype.DelayedProto~ uses Lean ~Thunk~ for non-function lazy instances.
[[file:../Examples/PrototypeCore.lean][PrototypeCore.lean]] runs these constructions directly.
~Prototype.Object~ pairs a lazy instance with its reusable prototype;
[[file:../Examples/FirstClassObject.lean][FirstClassObject.lean]] shows extension
and object-to-object mixing after instantiation.
~Object.recordSlotGen~ builds a delayed typed record slot without forcing
final self while assembling the record. [[file:../Examples/FirstClassRecord.lean][FirstClassRecord.lean]] shows a
computed slot observing a later override through the new final self.

~Prototype.Chain~ composes prototypes whose intermediate types differ;
~Chain.append~ joins chains only when their endpoint types match, and Lean
checks its associativity and interpretation laws.
~Prototype.composeAll~ handles a homogeneous list through the same chain.
~DelayedProto.Chain~ gives the delayed construction the same type-indexed
composition; its homogeneous list form uses that chain's interpreter.
~Prototype.constant~ can close a chain without using the external base;
[[file:../Examples/PrototypeFunctions.lean][PrototypeFunctions.lean]] uses it
to compose a numeric function from reusable increments.
~Prototype.lensGen~ is the appendix's typed getter/wrapper/setter constructor
for a method fragment. It returns a normal delayed prototype;
[[file:../Examples/LensPrototype.lean][LensPrototype.lean]] shows its use.
~Prototype.Record~ is the direct record-as-function model from the paper.
~Record.slotGen~ owns its slot construction, with ~slot~, ~modify~, and
~compute~ as specializations. ~Record.instantiate~ closes a composed record
prototype; [[file:../Examples/RecordPrototype.lean][RecordPrototype.lean]]
shows self-dependent slots and inheritance order.
~Prototype.instantiate~
ties a function-valued prototype to one shared open-recursive result. Such a
prototype uses ~FixedFunction Input Output~ as its instance type; ~CoeFun~
lets that value be called with ordinary function syntax. The additional
runtime field prevents Lean from eta-expanding prototype construction into
each call. The general recursive knot is ~unsafe~ because it may diverge; it
does not require an ~Inhabited~ result type.

| Operation | Role |
|-----------+------|
| ~Object.Declaration.empty~ | Start a typed declaration. |
| ~Declaration.build~ / ~buildOn~ | Run a pure, reusable Lean ~do~ program to construct or extend a typed declaration. |
| ~Declaration.Builder.value~ / ~default~ / ~slot~ / ~modifyInherited~ / ~edit~ | Compose direct values, defaults, open methods, delayed inherited updates, and ordinary declaration transforms. |
| ~Prototype.SkewLens.focus~ / ~refocusUpdate~ | Lift an open prototype to a wider context and narrow its update target independently of the final-self view. |
| ~Prototype.MonoLens~ | Compose ordinary getter/setter field focuses as a special case of skew lenses. |
| ~Declaration.Builder.focusInherited~ | Apply a focused change to an inherited slot value while retaining the rest of the value. |
| ~Declaration.Builder.skew~ | Install a general skew-focused open extension as a delayed C4 slot method. |
| ~Declaration.withSlot~ / ~withDefault~ | Add a slot computation or base default at a typed key. |
| ~Declaration.fromValues~ / ~fromValuesIndexed~ / ~fromFunction~ / ~fromMap~ | Build ordered direct slots from typed values, a hash-indexed value stream, a lazy function, or a sorted dependent map. |
| ~LeanPoo.mix~ | Add a node with ordered direct supers and compile its C4 plan. |
| ~LeanPoo.mixC4~ | Add a node with complete C4 parent orders and suffix metadata. |
| ~LeanPoo.extend~ | Add a node with one parent and compile its C4 plan. |
| ~LeanPoo.plus~ | Apply Gerbil's ~.+~ shape to a flat override and base. |
| ~LeanPoo.clone~ | Copy one object's direct slots, defaults, and topology, replacing selected typed values. |
| ~Memoized.extend~ / ~mix~ / ~plus~ / ~clone~ | Continue composition from an executable object and create a fresh lazy instance. |
| ~Plan.toFirstClassObject~ | Construct the paper's first-class instance/prototype pair from a typed C4 slot plan. |
| ~Memoized.toFirstClassObject~ | Project a C4 object into that pair while retaining its memoized current instance. |
| ~Memoized.mixWith~ | Compose independently built objects after rejecting colliding node names. |
| ~Memoized.reviseSlot~ / ~reviseDefault~ | Persistently update a prototype declaration and instantiate its new result. |

The resulting ~Object.Plan~ contains its C4 precedence and a proof that the
linearizer returned that order. ~plus~ rejects an override with multiple
C++ local parent orders rather than flattening them silently. ~clone~ rejects
duplicate override keys and validates its new node through C4.

For wide sets of direct values, ~Declaration.fromMap~ sorts map entries once.
~fromValuesIndexed~ instead preserves the first occurrence order of its input
keys while the last value at each key wins. It indexes array positions by key
and replaces only the affected array element. ~fromValues~ retains its
~DecidableEq~-only key requirement and the same ordered overwrite behavior for
keys without a hash implementation. ~just benchmark-declaration~ measures all
three construction paths; the fixture is a construction benchmark, not a
theorem replay benchmark.

[[file:../Examples/TypedSlots.lean][TypedSlots.lean]] is a standalone Lean example of a key-indexed value family:
one slot contains ~Bool~, another contains ~Nat~, and a computed slot can
read final self and its inherited value with those types checked by Lean.
[[file:../Examples/DeclarationBuilder.lean][DeclarationBuilder.lean]] uses the public
builder to express ordered heterogeneous declarations with native ~do~ notation.
Its direct-value declaration is definitionally equal to the corresponding
~withValue~ chain; the example also evaluates an inherited method through C4.
[[file:../Examples/FocusedSpecification.lean][FocusedSpecification.lean]] composes two
field focuses, updates one nested retry count through inherited computation,
and checks that neighboring fields keep their inherited values after C4
resolution.
[[file:../Examples/SkewExtension.lean][SkewExtension.lean]] demonstrates a genuinely
skew extension: the method reads an enable flag from final self while
updating only the inherited retry count. It checks both the enabled and
disabled cases, states agreement with successive focusing, and installs a
skew-focused method in a C4 object declaration.
[[file:../Examples/LayeredObject.lean][LayeredObject.lean]] runs a complete ~mix~ / ~extend~ / ~memoize~ / ~read~ path.
It also clones the executable child with a new direct value. Composition
reuses the object's prototype information; the derived object receives its
own memoized values. The same example mixes two independently built object
families and reads both inherited slots. A diamond with a shared base shows
C4's precedence and the order of inherited method composition.
[[file:../Examples/IntegratedPrototype.lean][IntegratedPrototype.lean]] follows one C4 diamond through memoized
execution, first-class projection, a new override, and a mutable snapshot.

* Read slots

| Operation | Role |
|-----------+------|
| ~Plan.resolve~ | Query a typed slot; absence is ~none~. |
| ~Plan.ref~ | Require a slot; absence is ~noApplicableMethod~. |
| ~Plan.memoize~ | Build a shared lazy instance of an open-recursive plan. |
| ~Plan.memoizeCompiled~ | Assemble the effective method table once, then keep values lazy; useful for dense reads of a wide object. |
| ~Plan.compileMemo~ / ~CompiledPlan.instantiate~ | Compile the open method table once, then create any number of objects with independent lazy cells. |
| ~CompiledPlan.resolve_sound~ | For a materialized key, equate the compiled open method with ~Plan.resolve~ for every self. |
| ~Plan.memoizeIndexed~ | Index every declaration once, then compose a slot's method when its value is forced; ~IndexedPlan.resolve_sound~ proves its resolver agrees with ~Plan.resolve~ for every key and open self. |
| ~Memoized.read~ / ~ref~ / ~refWith~ / ~values~ | Read one slot, handle a missing slot explicitly, or materialize all slots from the shared instance. |
| ~LeanPoo.hasSlot~ | Check whether a key is declared in the C4 chain. |
| ~LeanPoo.hasSlots~ | Check several required keys in one compiled plan. |
| ~LeanPoo.allSlots~ | Enumerate declared keys in least-specific-first order. |
| ~LeanPoo.allSlotsSorted~ | Sort declared keys by an explicit Lean comparator. |
| ~LeanPoo.prepareDeclared~ | Store assembled slot functions in a dependent hash map. |
| ~Cache.read~ / ~Cache.ref~ | Return a value and an updated immutable instance cache. |
| ~Cache.peek~ | Inspect an existing cache entry without evaluating a slot. |
| ~Cache.rebase~ | Carry only selected evaluated entries into a new resolver and self, with a proof that each retained result is unchanged. |
| ~Proof.rebaseInstanceCacheByValue~ | Compare each cached value with the new resolved value and reuse only equal entries. |
| ~Cache.force~ | Fill cache entries for a finite set of keys. |
| ~Object.Closed.instantiate~ | Construct an instance when slots are independent of self. |
| ~Object.Ranked.instantiate~ | Construct a total fixed-point instance when every self dependency has a smaller natural-number rank. |
| ~Object.Dependencies.inferRanked~ | Infer and verify a rank from declared self dependencies; identify missing sources and blocked cycles separately. |
| ~Object.Dependencies.instantiate~ | Construct a proof-bearing fixed-point instance from checked finite dependencies. |
| ~Object.Instance.prepare~ / ~cache~ | Prepare and cache slots for one fixed-point instance. |
| ~Object.Instance.prepareDeclared~ / ~cacheDeclared~ | Use all declaration-owned keys. |
| ~Object.Cache.forceDeclared~ | Evaluate all declared keys into the explicit cache. |
| ~Object.Instance.values~ | Materialize typed key/value pairs in declaration order. |
| ~Object.Instance.select~ / ~Memoized.select~ | Read an ordered selection of typed keys. |
| ~Memoized.foldSlots~ | Traverse all declared typed values in object order. |
| ~Memoized.force~ / ~valuesSorted~ | Force every slot or export typed values in caller-chosen key order. |
| ~Object.Instance.cachedRead~ | Relate a cached result to the instance value. |

The declarations own their finite key order even when the Lean key type is
infinite. ~Prepared~ functions and ~Cache~ values carry proofs that they agree
with ~Plan.resolve~. Missing slots do not grow the value cache. ~memoize~ uses
Lean's call-by-need ~Thunk~ for each declared key.
~memoizeCompiled~ follows Gerbil-POO's base-to-child method-table pass,
including per-node last-write-wins declarations, and shares the same
~SlotSpec.toMethod~ and ~Method.compose~ operations. It moves method assembly
to object creation. [[file:../Examples/CompiledMemo.lean][CompiledMemo.lean]] checks the lazy and compiled paths on inherited defaults,
overrides, repeated local declarations, final-self reads, and missing keys.
The example also checks a C4 diamond. ~Plan.resolve_eq_compileSlot~ proves
that the standard resolver's parent-first fold equals its original C4 fold
for every key and open self. ~Entry.toMap_get?~ separately proves that the
compiled path's direct local writes keep last-write-wins declarations;
~Declaration.compileLocalMethods_get?~ specializes that fact to effective
methods. The builder makes no temporary per-declaration hash table.
The optimized table now carries a Lean equivalence theorem to ~Plan.resolve~
for every materialized key and open-recursive self. Choose it for workloads
that read many declared slots. ~memoizeIndexed~ preindexes each declaration and
keeps the same lazy values; its resolver has a general Lean soundness theorem.
The two accelerated paths have different construction/read costs, while
sparse reads can favor ~memoize~.
For repeated instances of one immutable C4 plan, call ~plan.compileMemo~ once
and then ~compiled.instantiate~ per instance. The compiled table retains open
methods, while each instance allocates its own shared lazy value cells.
~Plan.memoizeCompiled~ is the convenience form that compiles and instantiates
in one call. [[file:../Examples/CompiledMemo.lean][CompiledMemo.lean]] creates two instances from one compiled plan;
~just benchmark-memoization~ includes the separate ~compiledReused~ path.
~Memoized.mode~ records the chosen strategy. Derived objects from ~extend~,
~mix~, ~plus~, ~clone~, and declaration revision retain that strategy; when
~mixWith~ joins independent families, the left receiver supplies it.
~Plan.memoizeUsing~ selects a strategy explicitly. Mutable updates and
standard ~MutableProto.instantiate~ also carry the base object's mode, while
~instantiateCompiled~ explicitly selects compiled methods.
An unproductive cycle can diverge in either executable path. A proof-bearing
declaration needs an ~Object.Instance~ whose state satisfies the resolver
equation. ~Object.Ranked~ supplies one without unsafe recursion when the caller
proves that each resolved slot depends on self only at smaller ranks. For a
finite dependency support, ~Object.Dependencies.inferRanked~ schedules the
declared edges, reports an undeclared source with its reader, and checks the
derived rank before constructing ~Ranked~. ~Dependencies.instantiate~ then
returns the same proof-bearing instance in one call. The
caller proves that each slot reads only its declared dependencies; arbitrary
Lean functions cannot be inspected to infer that claim automatically.
[[file:../Examples/RankedObject.lean][RankedObject.lean]] constructs a child-computed slot over an inherited base
value, its fixed-point instance, and a sound cache. It also checks successful
rank inference, a declared cycle, and a missing source key. This discipline covers
well-founded dependencies; it does not decide whether arbitrary Lean slot
functions terminate.
~Dependencies.scheduleRanked~ retains the checked order and edge-rank proof.
~Scheduled.impact roots~ propagates direct edits through the declared reads
and checks that an unaffected slot cannot read an affected one.
~Scheduled.stableState~ proves that unaffected values agree between old and
new fixed-point instances when their resolver bodies agree at the old self.
~Scheduled.rebaseCache~ carries only those proved-stable evaluated entries to
the new instance. ~Dependencies.revise~ packages scheduling, impact checking,
fixed-point construction, and cache transfer in one declared update. The
caller supplies the unchanged-resolver proof; a change
to an opaque slot body cannot be inferred automatically.
~Proof.patchOfRevision~ turns that checked update into a patch over resolved
values. ~patchOfRevision_aligned~ proves that it produces the next fixed-point
state. ~CertifiedObject.applyRevision~ reuses obligations outside the
footprint and requests proofs for ~pendingRevision~. The integrated example
has two obligations: editing one inherited source selects its computed
relation for repair while reusing the independent relation.
~Instance.lazy keys~ builds shared Lean thunk cells from a proof-bearing
instance. ~LazyInstance.read_sound~ ties every read to that instance, while
~Revision.rebaseLazy~ retains a cell only outside the checked impact set and
installs fresh cells for affected selected keys. ~Revision.reusedLazyKeys~
reports retained cells without forcing them. This is the total ranked path;
ordinary ~Memoized~ still rebuilds its general recursive thunk table.
An unforced retained thunk may still hold the old instance through its
closure until it is forced or released. Callers with a strict retention
budget can use the explicit immutable ~Cache~ path, whose retained values
do not close over the old instance.
[[file:../Examples/IncrementalObject.lean][IncrementalObject.lean]] uses a C4 child
with two computed branches. Editing one inherited source invalidates its
dependent branch while preserving the independent source and computed cache.
~Object.Debug.Revision.explainImpact~ shows which dependency caused each
affected key. Run ~just check-incremental true~ for that report; normal checks
remain quiet.
~Proof.Runtime~ binds a certified instance, an explicit value cache, and
selected call-by-need cells into one persistent value. ~Runtime.revise~
performs the checked fixed-point update, transfers sound cache entries and
unaffected thunk cells, selects pending obligations, and closes the next
certificate. ~Runtime.read_sound~ and ~readLazy_sound~ relate both read paths
to the same instance. ~Runtime.newLoaded~ can prepare selected cache entries
before sharing a snapshot. ~Proof.MutableRuntime~ stores that value in an
~IO.Ref~. ~read~ memoizes explicit cache entries, while ~readLazy~ accesses
the shared thunk cells. ~snapshot~ retains an immutable view, and ~install~
accepts a fully certified next value only when the
snapshot version is still current. The integrated example checks old and new
reads, retained independent values, a stale install, and the certificate's
agreement with the installed instance. ~MutableRuntime.transact~ applies a
pure certified update to the current cell value in one operation; an error
preserves the version and cached contents. The version counts semantic
installs, not cache reads. Callers that use ~Runtime.revise~ separately must
derive the next value from the snapshot they intend to replace; the expected
version rejects intervening semantic installs.
Unforced reused thunk cells can retain their former instance closure. Use the
explicit cache read path when that retention matters; the pure revision
preserves its evaluated values without retaining those closures.
~Cache.rebase~ is a sound reuse primitive for the explicit immutable cache:
the caller selects reusable keys and proves equality of their old and new
resolved values. A key without that proof is omitted and follows the ordinary
read path on the new object. ~Proof.rebaseInstanceCache~ derives that equality
for keys outside a patch's *value-change footprint* from the old and new
~Object.Instance~ equations, the patch frame, and state alignment. Computed
slots whose values change must also be in that footprint, even when the edit
directly names only another slot. [[file:../Examples/CertifiedCacheReuse.lean][CertifiedCacheReuse.lean]] demonstrates both
single-slot reuse and a computed dependent that must be invalidated with its
source slot. The dependent example now constructs both instances through
~Object.Ranked~, closes a relation certificate after the patch, and rebases
the old cache. The footprint is supplied with a proof of state alignment; this
API does not infer arbitrary slot dependencies. When dependent values have
decidable equality, ~Proof.rebaseInstanceCacheByValue~ can instead compare each
stored value with the new resolver. This detects changed computed slots without
a supplied footprint and does not recompute the old instance. It may evaluate
the new instance and does not reuse the executable ~Memoized~ thunks.
Declaration-only revisions retain the plan's proved C4 precedence and create
a fresh memoized instance; an already instantiated object retains its values.
~Plan.reviseDeclarations~ and ~Memoized.reviseDeclarations~ apply ordered edits
to several existing nodes without recompiling the unchanged graph or
allocating an instance after each edit. A missing node returns a C4 error.

* Classes and mutable objects

~Prototype.DescriptorClass~ is a delayed prototype for a runtime
~Descriptor α~. Lean's ~α~ supplies the static type; ~accepts~ can recognize
a refinement. ~Descriptor.refine~ composes runtime predicates;
~listOf~, ~arrayOf~, ~optionOf~, ~pairOf~, ~sumOf~, and ~stringMapOf~ construct
descriptors over Lean's native type constructors; ~exactly~ and ~oneOf~ refine
one type by equality or finite enumeration. ~Descriptor.withJson~ uses Lean's ~ToJson~ and
~FromJson~ instances, and ~encodeJson~ / ~decodeJson~ enforce the refinement
at the JSON boundary. ~encodeText~ / ~decodeText~ use JSON text, while
~encodeBytes~ / ~decodeBytes~ use the same checked codec in a Lean-native
UTF-8 JSON representation. ~Descriptor.fin~ uses a
bounded Lean natural with a checked decoder; ~top~ and ~bottom~ recognize
every value and no value, respectively. ~Descriptor.bytes~ accepts arbitrary
byte arrays, while ~bytesN~ checks a fixed size. ~union~ and ~intersect~
combine refinements over one Lean type. ~functionOf~ records a typed function
shape, and ~checkedCall~ checks argument and result refinements.
~Descriptor.mapOf~ uses an explicit ~TextCodec~ for non-string map keys and
rejects collisions after decoding. ~withPrototypeValue~ validates a
descriptor's default value; parameterized list, array, map, and option
descriptors supply their native empty value.
~Prototype.HList~ represents heterogeneous tuples with a type-level list;
~Descriptors~ derive their runtime recognizer and JSON codec. ~TypedValue~
stores a descriptor, value, and proof of acceptance together. Number
descriptors include integer ranges, fixed-width ~BitVec~, and normalized
~Rat~ values.
[[file:../Examples/DescriptorClass.lean][DescriptorClass.lean]] demonstrates
inheritance and parameterization. ~Object.Mutable~ holds a persistent
~Memoized~ object in an ~IO.Ref~. ~reviseDeclaration~ and ~extend~ install a
fresh C4-validated instance on success. The example in
[[file:../Examples/MutableObject.lean][MutableObject.lean]] shows this path.
~Mutable.reviseDeclarations~ installs a complete ordered batch in one cell
operation. If any edit fails, the old object and its cached reads remain
current. The same example edits an inherited base and child computation
together, then checks rollback for an unknown node.
~Prototype.MutableProto~ is the paper's one-identity mutable wrapper in
Lean. ~compose child parent~ runs the parent first and then the child on the
same ~Object.Mutable~ cell. ~composeAll~ accepts a most-specific-first list;
~extend~, ~slot~, and ~revise~ construct layers from the existing C4 object
operations. ~instantiate~ starts from a memoized base and exposes the cell
only when every layer succeeds. A composition made entirely of these standard
layers stages its schema changes, compiles C4 at most once for the final root, and
allocates one final lazy instance. Duplicate names and unknown revision targets
are rejected at the layer that introduces them. A custom ~apply~ effect falls
back to sequential private execution.
~instantiateCompiled~ selects the optional precompiled effective method table
for the final instance without first allocating an on-demand instance on the
standard private path. Applying a layer directly to an already shared cell
always has sequential effect semantics, so a later failure may leave earlier
layers installed. [[file:../Examples/MutablePrototype.lean][MutablePrototype.lean]] compares the batched and sequential paths with pure
extension, checks a late override of a ~self~-dependent slot, custom-effect
fallback, and failed private and shared builds. The identity prototype keeps
the supplied memoized base, including its existing lazy cells.
The standard path retains ~Plan.resolve~; the compiled path uses the same
~SlotSpec~ method algebra with a preassembled effective table.
~putValue~, ~putSlot~, and ~putDefault~ revise the current root declaration
and replace its lazy instance. Existing snapshots retain their old values;
[[file:../Examples/IntegratedPrototype.lean][IntegratedPrototype.lean]] shows a dependent slot recomputed after
~putValue~.
~Object.Generic.fromSlot~ selects a typed method value from that same
memoized instance; ~Generic.fromType~ selects from an explicit descriptor.
~Generic.call~ applies the chosen method or a typed fallback. The integrated
example uses a numeric method value to scale an input before and after C4
extension.
~Object.ClassSpec~ and dependent ~SlotRule~ values describe required,
optional, fixed, and computed slots. ~ClassSpec.toDeclaration~ creates a
normal C4 declaration; ~toDescriptor~ checks an existing memoized object.
~ClassSpec.instantiate~ constructs one from its defaults and computations.
~ClassSpec.layer~ makes a delayed class prototype whose child rules override
matching parent rules; an ordinary ~Prototype.Object~ retains that class
prototype with its derived descriptor.
~ClassSpec.effectiveRules~ resolves repeated declarations of one key once
for construction, validation, and JSON conversion.
~encodeJson~ / ~decodeJson~ use explicit slot codecs and preserve computed
specifications when direct values are decoded. ~SlotRule.fromDescriptor~
shares validation and JSON behavior with a typed descriptor. Fixed and
computed slots are rebuilt from the class instead of appearing in encoded
JSON. ~decodeObjectJson~ compiles
and validates a full object. A sealed class rejects unknown JSON fields.
~Object.Lens.slot~ gets, sets, or modifies a typed slot through persistent
C4 recompilation; ~Lens.compose~ combines two typed lenses.

* Compose proofs

| Operation | Role |
|-----------+------|
| ~Proof.Obligation~ | State a proposition, its dependency keys, and a stability proof. |
| ~Proof.Patch~ | Change state with an explicit touched-key set and frame proof. |
| ~Proof.Patch.set~ | Override one typed key with an automatically derived frame proof. |
| ~Proof.Patch.setMany~ | Apply ordered typed overrides; the final write at a repeated key wins. |
| ~Proof.Patch.composeAll~ | Compose existing patches in order through one fold. |
| ~Proof.pending~ | Select old obligations affected by touched keys, plus new obligations. |
| ~Proof.closePending~ | Build a certificate from reused and newly discharged proofs. |
| ~Proof.invalidatedNodes~ | Compute graph nodes affected by a structural change. |
| ~Proof.mem_invalidated_of_descendant~ | Prove inclusion for a parent-to-child path within the graph's propagation bound. |
| ~Proof.mem_invalidated_iff_bounded_descendant~ | Characterize the complete output as exactly those nodes with bounded paths from changed nodes. |
| ~Proof.CertifiedObject.applyPatch~ | Bind the new certificate to a C4-valid instance. |
| ~Proof.rebaseInstanceCache~ | Preserve cached values outside a proved patch footprint while rebinding to a new C4-valid instance. |
| ~Proof.ProofObject.pair~ | Combine independent proof objects under disjoint ~Sum~ keys. |
| ~Proof.Certificate.pair~ | Combine their certificates without replaying either proof. |
| ~Proof.Patch.left~ / ~right~ | Lift a patch into one side while preserving the other side. |
| ~Proof.ProofObject.withObligation~ | Attach a relation that spans composed components. |

The domain supplies its concrete keys, values, propositions, and
instances. Structural node invalidation and value-key dependency
selection are separate operations. ~append_composeAll~ proves batch append
agrees with stepwise append; ~unaffected_composeAll_iff~ characterizes proof
reuse across the entire batch.

* Debugging recursive objects

~Object.Debug.Plan.explain~ reports C4 precedence and the nodes that
declare a requested slot without forcing its value.
~Proof.Debug.explainPatch~ reports each obligation's dependencies, the keys
touched by a patch, and whether it needs a new proof.

For agent-authored recursive slot computations, ~Object.Debug.Program~
provides an explicit self-read function. ~runTrace fuel key~ returns typed
enter, resolve, missing, cycle, and exhaustion events, the result, and
~stepsUsed~. The fuel is shared by every read in one run, including sibling
reads; event recording uses a reverse accumulator to keep each append constant
time.
~run fuel key~ returns only the result. Both report a cycle with its
complete key path or stop when the fuel budget is exhausted.
[[file:../Examples/DebugObject.lean][DebugObject.lean]] shows a two-slot
cycle, a productive dependency, and a branching case that exhausts the shared
budget.
The shared budget covers reads made through this interface. An opaque Lean
callback can still block without making another read, and ordinary
~Memoized.read~ retains its original lazy semantics. Callers needing a
bounded process must run diagnostics in an isolated Lean process with an
external deadline. The public debug API can be imported by downstream users.
~just check-debug~ verifies normal traces with a 30-second process timeout,
2048 MB Lean memory ceiling, and allocation budget. It also runs an opaque
blocking callback in a separate process and checks that the two-second
external timeout terminates it. These limits protect the test process; they
do not prove termination of an arbitrary callback or bound the total memory
of another host application embedding this API.
~just check-debug true~ prints those reports on demand. Lean's ~-v~ reports
its version and Lake's ~--verbose~ reports build commands, so the Justfile
parameter controls semantic trace output separately. For finite declared
dependencies, rank construction rejects cycles before evaluation and no
per-read guard is needed. The optional ~Debug.Program~ remains available for
opaque agent-authored computations that cannot supply that declaration.

~just check-proof-reuse~ constructs 10,000 independent obligations through
the public Debug impact API. A single-key patch selects one for repair and
reports 9,999 reusable obligations. This checks dependency selection at scale;
it does not measure theorem replay time or represent a large Cedar policy
corpus.

* Commands

~just check-c4~, ~just check-object~, ~just check-compose~,
~just check-po~, and ~just check-proof~ compile the respective layers.
~just benchmark-revision~ compares full C4 recompilation with a
declaration-only revision on a synthetic 64-node chain. It measures topology
updates, not object reads or cross-platform performance.
~just benchmark-memoization~ compares sparse and dense reads of 256 direct
slots through the on-demand, compiled, indexed, and compiled-reused paths;
it also runs a 64-node chain. ~just benchmark-c4~ measures C4 construction
on deep chains and wide fan-in graphs. These are synthetic local timings;
the workload should determine which constructor to use.
~just check~ compiles the
complete library. These are Lean elaboration and theorem checks, not a
duplicate upstream reference-test suite.
