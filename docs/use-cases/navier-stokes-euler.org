The source already uses Lean structures and inherited projections, for
example ~EulerMeanPacketProvider.Budget extends SobolevData~. Packaging common
arguments in an ordinary dependent context record is therefore the necessary
baseline. C4's additional role is selecting among interchangeable, typed
providers and preserving their precedence across multiple inherited families.
An import dependency graph alone does not justify applying C4 ordering.

* Functional API experiment

[[file:../../Examples/ContextualFactories.lean][ContextualFactories.lean]] uses five capability keys: background,
derivative, residual, linear, and quadratic. Its topology joins initialized
fields with correction coefficients, then derives a residual-only override:

#+begin_example
TightResidual → SpatialBudget → InitializedFields → CorrectionCoefficients → Source
#+end_example

This is a proposed provider topology, not a transcription of upstream module
imports. ~Inputs Context Value~ retains the five existing factories.
~Value : Context → Capability → Type~ lets the application supply actual
upstream mathematical types. ~compileFamily~ obtains a verified C4 order and
assembles the provider family. Generic kernel examples prove the override
selects the new residual factory while retaining the old background factory.
No scalar surrogate is used to claim a Navier–Stokes or Euler theorem.

The library interface in ~LeanPoo.Functional.Assembly~ supplies:

- ~Factory~ and ~Provider~ for context-dependent functions.
- ~assemble~ for selection through a retained verified order.
- ~assemble_origin~ for original-graph provider provenance.
- ~apply_selected~ for application of the selected function to the exact context.

This preserves the existing analytic proofs as callbacks. A revised field or
parameter must still produce a proof of the exact new result type. Mathematical
proofs are not replaced by C4, and open-recursive unsafe instantiation is not
needed for this factory interface.

* API lessons from the reference

The repeated context arguments in ~initializedSpatialBudget~ motivate a
consumer workflow, implemented entirely within LeanPoo:

1. Retain an ordinary dependent context containing the data and guards.
2. Keep existing constructors as ~Factory Context Result~ functions.
3. Compile the provider graph once with ~linearizeVerified~ and ~assemble~.
4. Declare the consumer checklist and call ~Requirements.prepare~ before the
   repeated order/time/context loop. Failure returns the first missing typed key.
5. Retain the resulting functions. ~Factory.zipWith~ passes both results at
   the same context to a consumer's existing constructor.
6. Use ~Factory.reindex~ when a consumer has a larger context. Its explicit
   projection determines the result type; it cannot silently move a proof
   to changed data.

[[file:../../Examples/ContextualFactories.lean][ContextualFactories.Prepared]] uses the library's dependent requirement tuple
for ~[background, residual]~. The same API accepts the full spatial checklist
~[background, derivative, residual, linear, quadratic]~ without a new preparation
record or another sequence of ~require~ calls. ~Requirements.build~ invokes the
retained functions at the supplied context and returns the corresponding typed
results. The consumer supplies its existing budget constructor.

~prepare_ok_iff~ identifies every retained factory; ~prepare_origin~ supplies
original-graph provenance for each requested key. A context can include finite
Sobolev order and guards; factories still return the witness at that exact
indexed type. This experiment does not instantiate upstream spatial budgets.

* Functional cases and maintenance boundaries

At the same source pin,
[[https://github.com/openai/NavierStokesAndEuler/blob/f9e8bc5b38b6e212696e8a30e3e91517af887bbd/Euler/FunctionalVelocity.lean#L15][EulerFunctionalVelocity.velocityMap]] takes an indexed family of four bounded
linear functionals; ~velocityMap_apply~ immediately identifies each output
component with its supplied functional. Its fixed coordinate assembly already
uses ordinary Lean composition well. C4 selection is useful only if a consumer
has interchangeable implementations with an actual precedence policy.

The budget factory case has a different proposed seam: initialized estimates,
correction coefficients, and a residual-only override can contribute separate
capabilities. One checklist prepares the full combination. The consumer retains
that prepared tuple across order/time calls instead of repeating selection.

| Maintenance change | What the client changes | Reused evidence |
|--------------------+-------------------------+-----------------|
| Add a required field | Extend the typed checklist and consumer constructor | Generic preparation and provenance contracts |
| Replace only residual | Supply its new factory in the more-specific provider | Other selected factories and context/result types |
| Change data/order/guards | Supply a new exact context; factories construct fresh indexed results | Selection of retained functions |
| Prefix provider names | Rename graph and align dictionary entries under those names | ~assemble_rename~ proves identical selected functions |
| Rename graph only | Preparation can fail; fix dictionary alignment | No selection-preservation claim without alignment |

This is a design study with executable generic clients. No upstream module is
copied, changed, imported, or built. It establishes reusable interface contracts,
not a measured reduction of Euler source lines or analytic proof cost.

Binding repeated arguments is a benefit of ordinary Lean functions and
context records. C4 adds selection and precedence across a proposed provider
family. The source's import graph is not itself such a family. Mathematical
proofs still need their original guards, including order and radius bounds.

* Evidence and limits

At this snapshot, the local import closure of ~Euler.PacketParentNormalBudget~
contains 317 upstream source modules and 56,066 source lines, before Mathlib.
This is a dependency-size receipt, not proof complexity or performance data.
~sourceNormalBudget~ has one external source call site, in
~Euler/PacketParentLabelBudgets.lean~. That single call does not justify a
claim of large source reduction from C4.

No upstream source is migrated or removed. The maintained output is a generic
LeanPoo API, its kernel-checked client contracts, and usage guidance informed
by the reference. Net PDE source reduction and performance improvement are
not established. Any later comparison must count context records, adapters,
provider declarations, and consumer code together, and distinguish argument
packaging from C4's contribution.
